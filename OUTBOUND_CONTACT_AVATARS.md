# Аватар контакта при создании диалога — дополнение 11.11

Вариант 1 согласован пользователем 25.10.2026: небольшой аватар в результате поиска, полноценное фото сохраняется при нажатии «Начать диалог».

## Поиск

`GET /api/channels/{channelAccountId}/telegram/find` сохраняет поиск по телефону или username. Необязательное nullable поле `avatarPreview` содержит `contentType` и `base64`. Поиск и чтение фото выполняются через `ChannelConnectorRegistry → IChannelConnector`; Telegram реализует общие команды `DiscoverClientAccountCommand` и `ReadClientAccountAvatarCommand`.

Для preview берётся `ProfilePhoto.small` (160×160), не более 256 KiB исходных байтов. Допускаются JPEG, PNG и WebP, MIME определяется по содержимому. Поиск ограничен 10 секундами, дополнительное чтение preview — 3 секундами. Недоступное фото не превращает найденный контакт в ошибку.

Поиск не создаёт ClientAccount/Conversation и не пишет `IAttachmentStorage`. Ответ имеет `Cache-Control: no-store`; UI также запрашивает его с `cache: no-store`. Превью хранится в состоянии окна и отображается через Blob URL. Новый поиск, закрытие, смена канала/Workspace/сессии отменяют запросы и отзывают URL; устаревшие ответы не меняют новую карточку. В localStorage/IndexedDB фото не сохраняется. TDLib использует собственный файловый кеш скачивания; отсутствие записи в ClientBus не означает отсутствие SDK-кеша на диске.

Перед поиском и после внешнего вызова проверяются актуальные права. Персональное Telegram-фото (`isPersonal`) разрешено только в предпросмотре выбранного подключённого аккаунта; оно не становится глобальным аватаром ClientAccount.

## Создание и постоянное хранение

UI отправляет прежний `CreateOutboundConversationRequest`, без Base64, storageKey или TDLib file ID. BE заново получает большое фото `ProfilePhoto.big` (640×640) по выбранным channelAccount/externalId. Общее ожидание GetUser и загрузки полного фото ограничено 5 секундами, размер — 5 MiB. Это отдельное чтение настоящего аватара, а не сохранение маленького preview.

`OutboundConversationService` выполняет внешние вызовы и запись файла вне транзакции БД. Короткая транзакция повторяет ACL/connected-проверки, создаёт либо переиспользует ClientAccount/Conversation и записывает `ClientAccount.avatarUrl`. Ручной аватар Client не меняется. Если фото отсутствует, недоступно или storage выдаёт ошибку, диалог создаётся с прежним аватаром либо с заглушкой. Автоматическая фоновая очередь повторов этой доработкой не вводится.

Параллельное создание использует блокировку и refresh существующего ClientAccount; коллизия вставки глобальной identity повторяется в новой транзакции после rollback. Изменившийся за время скачивания avatar key не перезаписывается устаревшим результатом. Идентичные сохранённые байты переиспользуются; проигравший upload удаляется. При ошибке создания очищается только собственный новый файл. После commit или при неопределённом исходе commit потенциально используемый файл сохраняется. Ошибка cleanup не подменяет исходный результат.

Прежний файл при замене avatarUrl автоматически не удаляется: на тот же storageKey может ссылаться ручной аватар Client. Персональное фото также исключено из существующего Telegram profile-download helper, чтобы последующая синхронизация не записала его глобально.

`ClientAccountEntity` использует `@DynamicUpdate`: изменение имени, телефона или привязки к Client записывает только изменённые колонки. Входящая транзакция, прочитавшая аккаунт до сохранения нового аватара, больше не восстанавливает прежний `avatarUrl` при своём позднем commit. Существующая блокировка и сравнение avatar key продолжают защищать параллельное создание диалогов. Схема БД не меняется.
