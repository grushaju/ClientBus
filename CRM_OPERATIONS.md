# 12.6 — управление визитами: реализация и границы

Работа начата 08.11.2026 по поручению пользователя; локальные проверки — 08–09.11.2026. План: [CRM_OPERATIONS_PLAN.md](CRM_OPERATIONS_PLAN.md). Базовые команды DIKIDI реализованы и проверены на тестовом аккаунте; границы W01–W04 уточнены в [CRM_OPERATIONS_ACCEPTANCE.md](CRM_OPERATIONS_ACCEPTANCE.md).

## Реализовано

- Типизированные `CrmCommandPort`, `CrmCommand`, `CrmCommandResult`, `CrmAvailability`. По умолчанию провайдер не разрешает ни одной команды. Объявление возможности означает подтверждённый протокол команды **и** её сверки. Дедлайн передаётся адаптеру; автоматический auth retry изменяющего запроса запрещён.
- Долговечная `crm.operation`: инициатор, ключ и SHA-256 нормализованного запроса, исходный контекст, версии, payload, результат и сроки. Уникальность ключа — проект/инициатор/ключ. Частичный уникальный индекс запрещает две незавершённые операции одного визита. Автор защищён от удаления. Hibernate добавляет таблицу существующим механизмом обновления схемы; отдельного migration framework не вводится.
- Допуск проверяет текущие права, настройки, контекст/часовой пояс, локальную версию визита или выбранных предложений. Создание использует существующего PROJECT CRM-клиента. Перенос ограничен полным визитом с одним мастером; снимок всех исходных полей, услуг, мастеров и финансов сохраняется без преобразования денежных чисел в Double. Неподтверждённые виды объектов не допускаются.
- Повтор с тем же ключом читает принятую операцию до проверки возможностей новой команды; другой нормализованный запрос даёт `CRM_IDEMPOTENCY_CONFLICT`. Работник повторно проверяет контекст, права, версии и доступность времени. Наблюдение доступности проверяется также после ожидания блокировок.
- Durable checkpoint `REQUESTED → IN_FLIGHT` фиксируется до внешнего изменения. Два работника могут выполнить чтение доступности, но право на команду получает только один. Сетевой вызов не удерживает транзакцию БД. Неопределённый ответ и истёкший IN_FLIGHT дают UNKNOWN, не новую отправку.
- Сверка UNKNOWN — отдельная операция чтения с ограниченной арендой. Отсутствие объекта само по себе не означает отказ. Терминальный исход требует доказательства от адаптера; поздний результат сохраняется в исходной операции даже после смены привязки. Первая терминальная запись не перезаписывается.
- После CONFIRMED сохраняются задачи перечитывания затронутых дней (для переноса — старого и нового) через существующий планировщик APPOINTMENTS. Прежнее успешное покрытие сохраняется; проекция меняется по результату чтения источника. Старый контекст не запускает чтения под новой привязкой. События используют существующий workspace outbox.

## REST

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/crm/projects/{id}/appointments` | Создание; обязательный UUID `Idempotency-Key` |
| POST | `/api/crm/appointments/{id}/move` | Перенос с ожидаемой локальной версией и новым localStart |
| POST | `/api/crm/appointments/{id}/cancel` | Отмена с ожидаемой версией и необязательной причиной |
| POST | `/api/crm/projects/{id}/availability` | Доступные начала для мастера, предложений и даты |
| POST | `/api/crm/appointments/{id}/availability` | Свободные начала переноса по услугам существующего визита; contextVersion, zoneRevision, expectedVersion, date |
| GET | `/api/crm/operations/{id}` | Локальное состояние операции |
| GET | `/api/crm/projects/{id}/operations/by-key/{key}` | Поиск текущего инициатора по ключу |
| GET | `/api/crm/projects/{id}/operations?own=true&active=false&cursor=...` | Журнал; до 50 строк, scoped cursor |
| GET | `/api/crm/appointments/{id}/history?own=true&cursor=...` | История одной карточки: до 50 действий, автор, время, перенос, комментарий отмены; scoped cursor |
| GET | `/api/crm/projects/{id}/pending-creations?cursor=...` | Свои незавершённые создания текущего контекста, включая UNKNOWN без карточки |
| POST | `/api/crm/operations/{id}/reconcile` | Явная сверка UNKNOWN без повторения команды |

Принятие возвращает 202 для REQUESTED/IN_FLIGHT/UNKNOWN и 200 для CONFIRMED/REJECTED. Обычный сотрудник видит свои операции; супервизор Workspace и администратор своей организации могут читать общий журнал. Все чтения проверяют текущий доступ. Ошибка авторизации DIKIDI не становится 401 ClientBus.

## UI

Во вкладке «Записи» остаётся «+ Запись»; общий список «Операции с визитами» и его фильтры удалены в 12.6.2. В карточке визита — перенос/отмена с подтверждением и сворачиваемая «История действий». История запрашивается только при раскрытии: автор, дата, результат, старое/новое время переноса и локальный комментарий отмены. Технические ID скрыты в деталях. Сотрудник видит свои действия; супервизор Workspace и администратор организации — все разрешённые действия карточки. Это история команд ClientBus, а не аудит сторонних изменений DIKIDI. Кнопки зависят от подтверждённых возможностей, текущей настройки и вида объекта. Изменение контекста/зоны сбрасывает незавершённую форму; версия визита фиксируется при её открытии.

Ключ сохраняется **до** POST в localStorage отдельно для Organization/инициатора/проекта. Web Locks сериализует проверку и запись между вкладками. Хранилище содержит только ключ, тип и operationId — без тела запроса и персональных данных. Невозможность сохранить ключ или отсутствие Web Locks останавливает отправку.

Потеря ответа, reload, logout и 404 lookup не освобождают ключ. UI показывает отдельный блок восстановления незавершённого создания в контексте проекта, включая действия, найденные на сервере без локального указателя. Сохранённое локальное намерение переноса/отмены также остаётся доступно для проверки. UI не пересоздаёт команду автоматически. В рамках одного браузера допускается одно незавершённое намерение на проект/инициатора; UNKNOWN удерживает его до доказанного исхода. Это сознательное ограничение первой реализации. Безопасно отклонённый допуск или терминальный результат освобождают указатель; серверный журнал сохраняет ключ.

Исправления ревью 09.11: ожидание Web Lock отменяется вместе с формой. Проверка отмены, сохранение ключа и начало POST выполняются под одной блокировкой без await между ними. Если отмена произошла до начала POST, ключ не сохраняется либо удаляется под той же блокировкой; после начала отправки ключ остаётся для сверки. Недоступную выбранную услугу можно снять, а исчезнувшие/выключенные предложения — убрать кнопкой «Сбросить выбранные услуги». Изменение выбора отменяет прежний результат проверки времени, остальные поля формы сохраняются.

## Реальный адаптер и восстановление

09.11.2026 на выбранном пользователем тестовом аккаунте проверены и включены CREATE_APPOINTMENT, MOVE_APPOINTMENT и CANCEL_APPOINTMENT. Реальным Java-адаптером выполнен цикл: создание 18 ноября в 12:00 → перенос на 25 ноября в 12:00 → отмена (Europe/Moscow). Каждый результат подтверждён отдельным чтением DIKIDI. Все известные созданные проверкой визиты отменены. Отдельно проверена потеря ответа после сохранения: read-only сверка нашла созданный визит по заранее сохранённому ID, без второго резерва или сохранения. Персональные значения и реальные ID в документацию не включаются.

ID резерва фиксируется отдельной транзакцией в crm.operation до окончательного сохранения. Потеря ответа после начала изменяющего запроса приводит к UNKNOWN; автоматической повторной авторизации с повтором записи нет. Ошибка до первого изменяющего запроса допускает доказанный REJECTED. Расходящийся ID результата не заменяет сохранённый ID резерва.

После CONFIRMED перечитываются затронутые дни и точный объект через master.record. Отменённый объект сохраняется в источнике со status_id=2 и deleted_datetime, хотя исчезает из дневного списка. Точечное чтение не объявляет остальные визиты отсутствующими. Историческое подключение, на которое ссылается операция, защищено от удаления после перепривязки проекта.

## Границы и следующие шаги

Поддержаны существующий PROJECT CRM-клиент, известные фиксированные услуги и один мастер. Перенос меняет только время при прежнем мастере; визиты с непустыми ресурсами отклоняются. Создание клиента, смена мастера, ресурсов и финансовые команды не реализованы. Комментарий к отмене сохраняется только в ClientBus. TTL/автоматическое освобождение незавершённого резерва не установлены: UNKNOWN не разрешает повторную отправку. Оплаченные, смешанные и ресурсные сценарии живым прогоном не проверялись. Кэш/защита от 429 — следующий подпункт 12.6.1; общая приёмка — 12.7.

## Исправления повторного ревью 09.11.2026

Перед переносом/отменой актуальный объект DIKIDI сравнивается с принятым локальным снимком: исходное начало и известное окончание, мастера и комментарий. Несовпадение отклоняет команду до внешнего изменения. Это проверка перед отправкой, а не обещание атомарной блокировки стороннего кабинета DIKIDI.

Перед изменением существующего визита его исходный объект DIKIDI отдельной транзакцией сохраняется в payload операции (`preservedSnapshot.providerBefore`). Ошибка сохранения останавливает команду. Непосредственная проверка и последующая read-only сверка используют один сохранённый снимок: изменение финансовых ссылок, комментария и остальных сохраняемых полей не превращает UNKNOWN в CONFIRMED. Старые неопределённые переносы/отмены без такого снимка автоматически подтверждаться не будут.

Точечные задачи RECORD являются одноразовыми: после получения нужного объекта и фиксации проекции сохраняется `observationCompletedAt`, и планировщик больше их не опрашивает. Ошибка или пустой ответ оставляют задачу доступной для повторного чтения. Новая подтверждённая операция снимает отметку завершения соответствующей задачи. Регулярные подписки периодов продолжают работать.

После исправлений прошли все 338 серверных CRM/DIKIDI тестов без ошибок и пропусков, включая шесть новых контрактных тестов адаптера и три PostgreSQL-регрессии. `git diff --check` прошёл. UI не менялся, браузерный набор повторно не запускался; дополнительных внешних изменений DIKIDI не выполнялось.

## Выбор времени создания записи — 09.11.2026

Ручное начало и кнопка «Проверить время» в форме создания заменены выбором рабочего интервала мастера и свободного начала внутри него. Список графика читается из локальной проекции за 31 день, период можно менять; загрузка следующих страниц и обновление графика доступны в форме. Показываются только WORK/WORKING выбранного мастера. При выборе интервала доступность DIKIDI автоматически запрашивается для даты, мастера и выбранных версий услуг. Время предлагается только из ответа доступности, с проверкой, что вся суммарная длительность услуг помещается в интервал; рабочая смена сама по себе не считается свободным временем.

Смена периода, интервала, мастера или условий услуг сбрасывает выбор времени. Ошибка/пустая доступность блокируют создание; доступно повторное чтение. Общие CRM-уведомления не вызывают повторных внешних запросов доступности, локальный график продолжает обновляться по событиям. Серверная повторная проверка перед командой сохраняется.

Прошли 20 desktop/mobile сценариев 12.6, включая выбор только внутри смены, границу длительности, пустой результат и повтор после ошибки; production build и типы e2e проверены. Протокол команд DIKIDI и серверный код в этом UI-дополнении не менялись.

Для переноса используется тот же выбор рабочего интервала и свободного времени; период изначально начинается с даты визита. Ручное поле «Новое начало» удалено. Новый read-only endpoint доступности проверяет доступ, контекст и версию визита, берёт исторические external service IDs из его полных услуг и прежнего мастера. Текущие предложения каталога и новые цены не подставляются. Версия визита повторно проверяется после внешнего чтения. Операция журнала при запросе доступности не создаётся. Неполные услуги/мастера не допускают ручного обхода выбора времени.

Дополнение переноса проверено 28 серверными тестами (PostgreSQL и HTTP), включая четыре новых проверки, и 22 desktop/mobile сценариями 12.6. Проверены типы e2e и production build.

## 12.6.2 — История карточки (11.11.2026)

Источник — существующая crm.operation. Действия связываются с локальным targetappointmentid; CREATE с NULL target связывается только после CONFIRMED по externalreference. Запрос ограничен проектом, текущими connection/credential/contextVersion и внешним проектом. Одинаковые внешние ID в разных проектах не смешиваются. Cursor привязан к карточке, автору, режиму доступа и контексту. Raw requestbody, payload и provider snapshots в истории не возвращаются.

Восстановление не удаляет ключ при 404 или смене контекста. Старый ключ продолжает запрещать повторную команду; ответ прежнего контекста не выводится в новом. REQUESTED/IN_FLIGHT проверяются повторным чтением, UNKNOWN — явной read-only сверкой. История и блок восстановления используют существующие invalidation/access lifetime, чтобы не применять поздние ответы после перехода или отзыва прав.

Проверки 11.11.2026: 50 серверных тестов операций/HTTP (23 PostgreSQL/Testcontainers, 27 HTTP), 489 UI-тестов, типы e2e и production build прошли. Полный CRM браузерный прогон — 78 desktop/mobile сценариев; после последней правки сверки из карточки повторно прошли 28 тестов карточек и 6 браузерных сценариев 12.6.2. Ресурсы перенесены через mvn -o process-resources. Логи: server/target/crm-history-server-tests.log, crm-history-ui-tests.log, crm-history-e2e-types.log, crm-history-browser.log, crm-history-card-final.log, crm-history-browser-final.log, crm-history-resources.log. Живые обращения DIKIDI, коммит и push не выполнялись; общая приёмка остаётся в 12.7. Для проверки приложения нужен перезапуск сервера.
