# Графики CRM — 12.4.3

Backend читает и сохраняет датированные рабочие интервалы одного мастера. Интервал графика не означает свободный слот для записи. Экран расписания относится к 12.5.

## Запрос и границы

Сначала мастер должен быть загружен в локальный каталог проекта. Используется его локальный UUID; UUID другого проекта не допускается.

```http
POST /api/crm/projects/{projectId}/refresh
Content-Type: application/json

{
  "dataset": "WORK_INTERVALS",
  "masterId": "локальный UUID мастера",
  "dateFrom": "2026-11-01",
  "dateTo": "2026-11-30"
}
```

Ответ — 202 и состояние выбранного набора. Границы дат включительные, максимум 31 день, годы 2000–2100. Это ограничения ClientBus. Для нескольких мастеров выполняются отдельные запросы; один активный SCHEDULE writer обслуживает проект. Повтор того же активного master/period объединяется с ним, другой scope до освобождения writer получает 429. Редактирование графика и запрос слотов не выполняются.

Локальное чтение:

- GET `/api/crm/projects/{projectId}/work-intervals?masterId={id}&dateFrom=2026-11-01&dateTo=2026-11-30&cursor=…`
- GET `/api/crm/projects/{projectId}/sync-state?masterId={id}&dateFrom=2026-11-01&dateTo=2026-11-30`

Первый endpoint возвращает до 100 интервалов, `nextCursor`, `hasMore`, `revision`, `dataState`. Интервалы содержат локальные даты/время, локальные ID, вид WORK, время наблюдения и ограниченные атрибуты. UTC и timezone из непроверенных полей DIKIDI не вычисляются. Чтение включает пересекающие период сохранённые интервалы; полнота снимка относится к датам начала смен в явно запрошенном scope.

`dataState` содержит прежние поля состояния и дополнительно `scope`, `successfulCoverage`, `attemptCoverage`. Scope явно называет мастера и даты. Последнее принятое наблюдение, последняя попытка и последнее подтверждённое полное покрытие различаются. GET sync-state без параметров сохраняет прежний набор состояний каталога и клиентов; с параметрами дополнительно возвращается состояние выбранного графика.

Cursor привязан к проекту, мастеру, датам и общей ревизии SCHEDULE. После новой загрузки или изменения контекста старый cursor требует начать чтение заново (`409 CRM_CONTEXT_CHANGED`). Чтение страницы и её состояния защищено одной SHARE-блокировкой проекта. Права Organization/Workspace проверяются для refresh, GET и при применении ответа worker; устаревший ответ после отзыва доступа не сохраняется.

## Хранение и применение

Добавлена `crm.workinterval`; Hibernate update создаёт таблицу без новой миграции. Внешние ID смен не объявляются устойчивыми ключами. Локальная уникальность — проект/мастер/начало/конец/вид; повторное наблюдение сохраняет ID существующей строки и ручное сопоставление мастера с Employee.

Полный подтверждённый ответ атомарно заменяет только смены WORK этого мастера, начавшиеся в выбранные даты. В том числе подтверждённый полный пустой снимок может очистить именно этот scope. Другие мастера, даты и служебные интервалы BLOCK/RESERVATION будущего домена визитов сохраняются. PARTIAL/UNKNOWN добавляет и обновляет положительные наблюдения, сохраняя отсутствующие прежние строки. Ошибка не меняет строки, `lastSuccessAt` или прежнее полное покрытие.

В `crm.syncstate` используются `WRITER:SCHEDULE/CONTROL` и отдельные scope-строки WORK_INTERVALS. Claim выдаётся до сетевого чтения, lease — 120 секунд; контекст фиксирует подключение, версии credentials/project/timezone. I/O выполняется вне транзакции. Перед записью повторно проверяются актуальность контекста и права; контекст защищён блокировками до конца транзакции. Claim и срок по часам PostgreSQL проверяются перед записью и после flush. Истёкшая аренда откатывает весь снимок; новый claim может выполнить безопасное повторное чтение. UI видит истёкшую попытку как `FAILED/CRM_REFRESH_EXPIRED`. Изменения публикуют `crm.invalidated` в транзакции, без персональных уведомлений.

## Автоматическая синхронизация

Первый явный refresh сохраняет запрос мастера/периода. Планировщик повторно читает эти сохранённые запросы по умолчанию раз в 5 минут, проверяя очередь каждые 10 секунд. Запросы переживают перезапуск server. Для одного проекта выбирается самый давно обновлявшийся период; затем кандидаты всех проектов сортируются по времени последней попытки, и только после этого применяется лимит свободных worker. UUID проекта используется для разрешения равенства времени, а не для приоритета обслуживания. Действующий SCHEDULE claim не дублируется. Сетевое чтение выполняет прежний worker с теми же ограничениями и проверками контекста.

По уточнению пользователя пересекающиеся периоды не получают дополнительных пометок устаревания. Их состояние описывает последнее завершённое чтение соответствующего периода. При следующей автоматической синхронизации worker получает новый снимок, обновляет БД и публикует `crm.invalidated`; подписанные UI-компоненты перечитывают данные и перерисовываются. Прежнее успешное полное покрытие сохраняется отдельно при неполном ответе или ошибке. Неподтверждённая полнота по-прежнему не разрешает удалять отсутствующие строки.

Внутри `syncstate.scope` сохраняется `refreshActorId`; это поле не выдаётся в публичном scope. Каждый запуск проверяет действующий доступ этого сотрудника к Workspace, включая проверку перед применением. Отзыв доступа или отключение сотрудника останавливает его автоматические запросы; новый разрешённый ручной refresh сохраняет актуального инициатора. Для запросов, сохранённых до появления планировщика и не имеющих инициатора, выбирается действующий SUPER_ADMIN той же Organization. JWT и браузерная сессия для работы планировщика не нужны. Отключённые проекты/подключения и подключения REAUTH_REQUIRED пропускаются.

Настройки server:

```yaml
clientbus:
  crm:
    schedules:
      enabled: true
      refresh-ms: 300000
      poll-ms: 10000
```

Планировщик использует отдельный `crmScheduleScheduler`, не блокируя обслуживание сообщений и уведомлений. Его инфраструктура создаётся независимо от JPA. Автоматическое обновление этого подпункта охватывает сохранённые запросы графиков; экран расписания реализуется в 12.5.

## DIKIDI: проверенная и непроверенная семантика

Используется owner R03 `masters.schedules`, а не online-слоты или вложенный `timeworks`. Параметры периода сверены с [закреплённой версией клиента](https://github.com/asbevz/dikidi-api/blob/d8a054341893533e4f3fce90101e2cd8ad180352/dikidi_api/endpoints/journal.py). Положительные наблюдения и ограничения A06 описаны в [CRM_DIKIDI_PROTOCOL.md](CRM_DIKIDI_PROTOCOL.md).

DIKIDI-адаптер возвращает **UNKNOWN** полноту: отсутствие даты в R03 пока не доказывает отсутствие смены. Даже пустой ответ не удаляет прежний график и не получает COMPLETE. Даты вне запроса не расширяют его покрытие. Ночные смены, непустые перерывы и несколько смен одной даты остаются непроверенными; неизвестный формат возвращает безопасную ошибку с сохранением данных. `begin/end`, `server_from` и внешний ID смены не используются для догадок о часовом поясе, рекуррентном правиле или устойчивой идентичности.

Полная замена проверяется на уровне SPI/PostgreSQL с явно подтверждённым COMPLETE. Включение такой семантики для живого DIKIDI требует доказательств в 12.4.6. Новые живые вызовы DIKIDI при этой реализации не выполняются.

## Проверка 04.11.2026

Уточнение 05.11.2026: общий адаптер DIKIDI различает локальную занятость сессии/HTTP-слотов (`CONNECTION_BUSY`) и настоящий HTTP 429 (`RATE_LIMITED`). После локальной занятости запрос графика или каталога становится доступен для повтора через min(refresh-ms, 10000) мс и запускается на очередном poll; выбор кандидата и проверка claim используют одно правило. Это позволяет двум доменам продолжить работу после освобождения одной сессии, не откладывая результат на 5 минут. Внешний rate limit сохраняет обычный интервал. Права, контекст, coverage, durable lease и данные предыдущей успешной загрузки сохраняются. Отдельные PostgreSQL-регрессии проверяют конкуренцию в обоих направлениях с настоящим адаптером поверх тестового транспорта.

Повторное ревью: отказ локального executor после проверки capacity также сохраняется как `CRM_CONNECTION_BUSY`, без ложной классификации как внешний 429. Ручной refresh получает 503, периодический запрос повторяется быстро после освобождения пула. PostgreSQL-регрессия воспроизводит заполнение обоих worker между выбором кандидата и отправкой задачи, затем проверяет повтор и успешную запись.

Полная серверная регрессия: 1081 тест, failures/errors/skips — 0. После финальных исправлений отдельно повторены 85 тестов `DikidiScheduleContractTest`, `CrmFoundationIntegrationTest`, `CrmHttpContractTest`, также без ошибок и пропусков. Проверены запрос/формат R03, UNKNOWN, полный/неполный/пустой снимок, сохранение ID и Employee links, чужие мастер/проект/организация, актуальные права, конкуренция, истечение lease до и после flush, смена подключения/timezone, cursor и Hibernate update. Полная замена сохраняет служебный BLOCK и не показывает его среди WORK-интервалов.
