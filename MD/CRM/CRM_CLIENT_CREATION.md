## Сценарий

- В таблице клиентов CRM рядом с именем отображается аватар из локального зеркала CRM; при отсутствии фото или ошибке загрузки — первая буква имени.

- Проект показан названием CRM и филиала. Единственный активный проект Workspace подставляется; при нескольких нужен явный выбор. Сейчас для DIKIDI БД разрешает один активный проект на Workspace, поэтому переписка его канала и форма используют тот же проект.
- Форма загружает контакты ClientBus, автоматически ищет во внешней CRM по выбранному телефону. Один номер подставляется; несколько требуют выбора. Поиск можно уточнить по имени или телефону. Первая порция ограничена 50 строками, при достижении лимита требуется уточнение.
- Для найденной карточки доступны выбор и отдельное подтверждение связи. Карточка, связанная с другим ClientBus, не предлагается для переназначения.
- Создание копирует имя, фамилию и один выбранный телефон. Значения редактируются только для CRM, исходная карточка ClientBus не меняется. При совпадении телефона требуется отметка «Это другой человек». Сервер независимо повторяет поиск непосредственно перед созданием.
- Создание аккаунта переписки, открытие диалога, отправка сообщения и перенос аватара в ClientBus не выполняются. Карточка CRM и чатовая учётка сходятся через существующий `dbo.client`, идентификаторы провайдера не отождествляются.

## Серверная операция

`crm.clientprovision` хранит ключ запроса, исходного клиента, автора, снимок контекста и контактов, подтверждённый внешний результат и состояние. Запрос принимается с `Idempotency-Key`; повтор с изменёнными данными отклоняется. Блокировка проекта сериализует принятие; незавершённая операция для того же клиента или телефона в проекте запрещает создание с новым ключом.

`REQUESTED → IN_FLIGHT → CREATED → CONFIRMED`. До внешней записи проверяются действующие права автора и контекст подключения. Внешний HTTP выполняется вне транзакции. Работник продолжает принятую операцию после закрытия формы. Истёкшая `IN_FLIGHT` становится `UNKNOWN` и никогда не отправляется заново. Достоверный отказ до отправки становится `REJECTED`.

Подтверждённая внешняя идентичность фиксируется отдельной транзакцией до локального связывания. После сбоя сохранения связи остаётся `CREATED`; восстановление работает с тем же внешним ID. После перезапуска работник подхватывает `CREATED` без зарегистрированной ошибки; после ошибки сотрудник может повторить восстановление из формы.

Для `UNKNOWN` сотрудник повторяет внешний поиск и явно подтверждает найденную карточку. Это ручное разрешение неопределённости с аудитом `RESOLVE_EXTERNAL`, а не автоматический вывод по совпадению телефона. Автоматически завершённое создание имеет аудит `CREATE_EXTERNAL`. Удаление клиента ClientBus блокируется до разрешения незавершённой операции; автора журнала можно отключить, но нельзя удалить.

Обычная ручка привязки не позволяет обойти незавершённое создание: разрешение `UNKNOWN` проходит через отдельное действие с аудитом. Повтор подтверждения той же карточки возвращает сохранённый результат, даже если ответ первого подтверждения потерялся. До отправки проверяется полный снимок конфигурации; при сохранении уже полученного результата проверяются стабильные организация, Workspace, провайдер и внешний проект. Ротация credentials, отключение и архивирование не блокируют завершение принятой операции. Восстановление не перезаписывает более свежие контакты уже импортированной карточки.

При повторном открытии формы поиск использует телефон принятой операции, даже если контакты ClientBus уже изменились. Неполный внешний поиск (`hasMore`) блокирует создание независимо от отметки «Это другой человек». Поиск импортирует только сведения справочника; статистику из списка DIKIDI не записывает поверх отдельной статистики клиента.

## API

| Метод | Маршрут | Результат |
| --- | --- | --- |
| GET | `/api/crm/projects/{id}/client-search?clientId=&q=` | Внешний поиск, импорт проверенных PROJECT-карточек, `items/hasMore` |
| POST | `/api/crm/projects/{id}/client-provisions` | `202`, операция; заголовок `Idempotency-Key`; тело `clientId/contextVersion/firstName/lastName/phone/differentPerson` |
| GET | `/api/crm/projects/{id}/client-provisions/latest?clientId=` | `{operation: null}` либо последняя операция, включая после повторного открытия формы |
| POST | `/api/crm/client-provisions/{id}/recover` | Восстановление локальной связи по сохранённому результату, без внешней записи |
| POST | `/api/crm/client-provisions/{id}/resolve` | Явное разрешение `UNKNOWN`: `crmClientId/expectedVersion` |

## DIKIDI: границы проверки

20.11 выполнено только авторизованное чтение существующего подключения: страница клиентов и `GET /ru/owner/ajax/clients/add/?company=…`. Подтверждены action `POST /ru/owner/ajax/clients/save/?company=…`, обязательные поля `name/number`, необязательная `surname`, отсутствие отдельного флага приглашения/уведомления в прочитанной форме. Контакты клиентов, cookies и секреты в отчёт не записаны.

Адаптер перед каждой записью повторно читает форму. Другой action, чужой проект или новое обязательное поле останавливают отправку. Изменяющий запрос выполняется один раз через общий DIKIDI-клиент, без повторной авторизации с повтором записи. Вход и поиск используют существующие транспорт и ограничитель.

**Живое создание выполнено 20.11.2026 по явному запросу пользователя** в проекте «Люстры из Анапы». Исходная операция `0b9876b4-4674-4315-a79f-82d0a63ee6ec` передавала российский номер с начальной `8`; save вернул HTTP 200 с `error: 1` и сообщением «Видимо вы неверно ввели номер». Это ошибочно отображалось общим кодом отказа доступа и оставляло неопределённый результат. После проверки отсутствия дублей по международному представлению того же номера выполнена исправленная запись. Создан ID `173521973`, существование независимо подтверждено поиском. Подтверждённый результат сохранён в исходный журнал, локальная связь завершена штатным методом завершения операции: `CONFIRMED`, правильный ClientBus clientId, errorCode отсутствует. Данные клиента ClientBus не менялись.

Реальный успешный save возвращает `client_info` (id/name/surname/phone без is_system), callback `$("body").trigger("clients.insert", data.client_info)` и HTML полного обновлённого списка. Адаптер проверяет идентичность контактов в `client_info` и маркер события, не принимает произвольный ID модального окна и не считает посторонние строки полного списка новыми клиентами. Явный наблюдённый отказ неверного телефона переводит операцию в `REJECTED` с `CRM_CLIENT_PHONE_INVALID`, без автоматического повтора; прочие неизвестные результаты остаются `UNKNOWN`.

Побочные уведомления самой DIKIDI отдельно не проверены. Отсутствие переданного флага уведомлений не доказывает отсутствие внутренних уведомлений DIKIDI.

Изменения кода требуют перезапуска сервера; таблица создаётся существующим бутстрапом `CrmStorage`. При описанной живой приёмке изменены внешняя CRM и состояние исходной операции/локальной связи.

- Фото ограничено 5 МБ и 16 млн пикселей; JPEG/PNG/GIF декодируются, центрируются в квадрат и перекодируются в PNG 512×512. Файл загружается через общий DIKIDI-транспорт: `POST https://f2.dikidi.ru/upload/?v=2`, multipart `file`, затем один POST формы профиля с image_id. Подтверждение — независимый поиск и совпадение CDN-ключа аватара у того же PROJECT ID. Только затем сохраняется локальное зеркало и публикуется CRM-инвалидация.
