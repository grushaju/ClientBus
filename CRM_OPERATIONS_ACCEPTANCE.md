# 12.6 — протокол проверки команд DIKIDI

09.11.2026 на выбранном пользователем тестовом аккаунте проверены и включены CREATE_APPOINTMENT, MOVE_APPOINTMENT и CANCEL_APPOINTMENT. Реальным Java-адаптером выполнен цикл: создание 18 ноября в 12:00 → перенос на 25 ноября в 12:00 → отмена (Europe/Moscow). Каждый результат подтверждён отдельным чтением DIKIDI. Все известные созданные проверкой визиты отменены. Отдельно проверена потеря ответа после сохранения: read-only сверка нашла созданный визит по заранее сохранённому ID, без второго резерва или сохранения. Персональные значения и реальные ID в документацию не включаются.

Поддержаны существующий PROJECT CRM-клиент, известные фиксированные услуги и один мастер. Перенос меняет только время при прежнем мастере; визиты с непустыми ресурсами отклоняются. Создание клиента, смена мастера, ресурсов и финансовые команды не реализованы. Комментарий к отмене сохраняется только в ClientBus. TTL/автоматическое освобождение незавершённого резерва не установлены: UNKNOWN не разрешает повторную отправку. Оплаченные, смешанные и ресурсные сценарии живым прогоном не проверялись. Кэш/защита от 429 — следующий подпункт 12.6.1; общая приёмка — 12.7.

Следующие разделы сохраняют последовательность проверок; фактический результат и пределы доказательств приведены ниже.

## Выбор тестового контекста

Перед внешним изменением нужно определить:

| Поле | Что выбрать |
|---|---|
| Подключение ClientBus | Существующее подключение DIKIDI; секреты не копируются в протокол |
| Проект / Workspace | Явно выделенный тестовый проект и его привязка |
| CRM-клиент | Существующий тестовый клиент с подтверждённой PROJECT identity |
| Мастер и услуга | Доступное предложение мастера с известными ценой, валютой и длительностью |
| Часовой пояс | Настроенная IANA zone проекта |
| Исходное / новое время | Два согласованных свободных начала для создания и переноса |
| Границы действий | Создание, перенос и отмена только нового визита этой проверки; без платежей, рассылок и изменения рабочих визитов |

Без этого выбора команды не отправляются. Реальные ID и персональные значения остаются в локальном контексте запуска; в итоговом протоколе используются условные обозначения. Авторизация берётся существующим способом, пароль не передаётся в командной строке.

## W01 — создание и возможный резерв

1. Зафиксировать исходное наблюдение выбранного времени, актуальное предложение и отсутствие созданного этой проверкой визита. Доступность не вычисляется как дополнение к занятости.
2. По подтверждённому owner-протоколу установить точные запросы, обязательные поля, признаки бизнес-ошибки и правило сверки. До этого команда остаётся закрытой. Если предусмотрен резерв, отдельно установить его ID, TTL и способ проверки; резерв не считается визитом.
3. Выполнить одну команду с одним локальным ключом. После начала эффекта не повторять запрос автоматически и не переавторизовываться с повторной отправкой.
4. Подтвердить целевой визит независимым чтением: проект, внешний ID, клиент, мастер, услуги, время, цена/валюта/длительность. Одного HTTP 200 недостаточно.
5. Проверить локальный CONFIRMED и последующее обновление проекции через чтение источника. Повтор локального POST с прежним ключом возвращает ту же операцию без нового внешнего создания.

Доказательства: очищенная схема запросов/ответов, правило идентификации объекта и сверки, количество изменяющих HTTP-запросов, состояние журнала и результат чтения. Сырые cookies/CSRF/данные клиента не сохраняются.

## W02 — перенос созданного тестового визита

1. Сохранить полный исходный снимок визита и независимых финансовых данных; неполные услуги/мастера закрывают перенос.
2. Подтвердить точный owner-payload изменения времени и read-only сверку; не выводить его из названия SDK-метода.
3. Перенести только визит W01 на согласованное новое время, с новым ключом операции и актуальной локальной версией.
4. Повторным чтением доказать новое время и сохранение клиента, мастера, состава услуг, исторических цен/длительностей, комментария, состояний, ресурсов и финансовых связей. Допустимые служебные изменения источника перечислить отдельно.
5. Проверить перечитывание старого и нового дня и обновление UI. Повтор прежнего ключа не вызывает второго внешнего переноса.

## W03 — отмена, не удаление

1. Установить явный owner-протокол отмены, признаки отменённого состояния и его отличие от удаления. `remove` не используется как замена неизвестной отмены.
2. Отменить только визит W01/W02 с актуальной версией и новым ключом.
3. Подтвердить отмену независимым чтением, проверить сохранение истории и финансовых связей, а также новое наблюдение доступности времени. Исчезновение строки из неполного списка не является доказательством отмены.
4. Проверить локальное состояние и UI. Не включать CANCEL_APPOINTMENT, если отмена или её сверка не доказаны, даже когда создание/перенос уже подтверждены.

## W04 — неопределённость и конкуренция

Сначала выполнить сетевые отказы на имитации подтверждённого протокола. Отдельный живой визит для проверки потери ответа выбирается явно; рабочий визит для этого не используется.

- Отбросить ответ после одной внешней отправки: операция остаётся UNKNOWN; reload/повтор локального ключа не отправляет команду ещё раз. Read-only сверка подтверждает однозначный исход либо сохраняет UNKNOWN.
- Проверить отказ до эффекта отдельно от timeout после эффекта. Отсутствие результата поиска само по себе не разрешает новый резерв/визит.
- Для двух конкурентных локальных попыток одного существующего визита только одна получает право начать эффект. Для разных ключей создания одинаковость полей сама по себе не обещает дедупликацию разных намерений.
- Проверить смену контекста и отзыв доступа до checkpoint, поздний ответ после смены контекста и восстановление после перезапуска. Старый результат сохраняется в старой операции и не проецируется под новую привязку.
- При 429 остановить живую последовательность и соблюсти Retry-After, если он известен. Не создавать нагрузку ради проверки лимита. Если 429 мешают, сначала реализовать защиту 12.6.1.

## Условия включения возможностей

Для каждой команды нужны подтверждённые payload, проверка ответа и read-only сверка. Они закрепляются отдельными контрактными тестами адаптера с очищенными фикстурами. После этого возможность включается отдельно, повторяются серверные и браузерные проверки и проводится явная приёмка на выбранных данных.

| Возможность | Протокол | Сверка | Контрактные тесты | Живой сценарий | Включена |
|---|---|---|---|---|---|
| CREATE_APPOINTMENT | Подтверждён в описанных границах | Точное чтение ID | Пройдены | Пройден базовый сценарий | Да |
| MOVE_APPOINTMENT | Подтверждён в описанных границах | Точное чтение ID | Пройдены | Пройден базовый сценарий | Да |
| CANCEL_APPOINTMENT | Подтверждён в описанных границах | Точное чтение ID | Пройдены | Пройден базовый сценарий | Да |

Живая проверка не запускается автоматически при обычном build/test. После проверки записываются дата, проверенная версия кода, сценарии и ограничения; реальные ID, секреты и персональные ответы не включаются в коммит. 12.6 закрывается только по фактически проверенным возможностям.

Сценарии выполнены на текущих локальных изменениях после HEAD 02f6cf8. Авторизация на изменения тестового аккаунта дана пользователем. Живой прогон не входит в автоматический build/test. Контрактные фикстуры очищены от реальных ID и персональных данных.

Дополнение повторного ревью 09.11: добавлены регрессии внешнего переноса/изменения мастера и комментария до команды, долговечного снимка перед изменением, потери ответа переноса/отмены и сохранности финансовых ссылок при сверке. Точечное обновление проверяется отдельно: ошибка → пустой ответ → объект → остановка опроса → повторная постановка новой операцией. Эти дополнительные проверки используют локальные фикстуры и PostgreSQL, без новых внешних изменений DIKIDI.
