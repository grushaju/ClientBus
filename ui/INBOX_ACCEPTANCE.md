# Inbox: регрессия и приёмка 10.10

Проверка выполняется после коммита `d8d7ffe` (этап 10.9).
Автоматические проверки и ручная приёмка учитываются отдельно: успешный запуск
тестов не означает завершения браузерных сценариев.

## Повторяемый прогон

Из корня проекта, PowerShell:

```powershell
npm --prefix .\ui test
npm --prefix .\ui run test:e2e:types
npm --prefix .\ui run test:e2e
mvn -o -pl server -am test-compile surefire:test
npm --prefix .\ui run build
mvn process-resources
```

Каждую следующую команду запускать только после успешного завершения предыдущей.
Для серверных интеграционных тестов нужен Docker с доступными образами PostgreSQL
и Kafka, для offline-режима Maven — предварительно загруженные зависимости.
При первом запуске без кеша убрать `-o`.

`npm test` собирает все `*.test.cjs` из `ui/tests`, включая Inbox, сотрудников,
переписку и подробности клиента. Поддерживающие модули не считаются тестами.
Серверный прогон не ограничен наборами 10.7–10.9: он включает коннекторы,
Kafka, репозитории, права, фильтры и запуск Spring-контекста.

Все наследники `AbstractIntegrationTest`, включая `ServerApplicationTests`,
используют профиль `test` и тестовые контейнеры. Проверка запуска приложения
не должна подключаться к БД и Kafka из обычного `application.yml`.
После каждого интеграционного класса Spring-контекст закрывается, пока общий
Kafka-контейнер ещё работает: клиенты Kafka не должны задерживать завершение JVM.

Используется `test-compile surefire:test`: эти цели компилируют приложение и тесты
и запускают весь набор; генерация HTML-отчёта и запуск отдельного сервера из
других фаз Maven в этот прогон не входят. XML-результаты находятся в
`server/target/surefire-reports`.

В ходе регрессии исправлены:

- Подключение `ServerApplicationTests` к обычной БД: класс переведён на общую
  интеграционную базу, тестовый профиль закреплён на базе.

  проверяет точный состав с учётом прежних записей и предикат фильтрации,
  идемпотентность сообщений — число сообщений своего диалога, отказ по неизвестному
  каналу — отсутствие изменений относительно исходных счётчиков.
- Закрытие Kafka producer при завершении JVM: Spring-контексты закрываются
  после каждого интеграционного класса, до остановки тестовых контейнеров.
- Маршрутизация DLQ: все DLQ настроены с одним partition, поэтому обработчик
  ошибок отправляет туда в partition 0. Прежнее сохранение номера исходного
  partition приводило к тайм-ауту для 1 и 2. Три новых unit-сценария проверяют
  исходные partition 0/1/2 и сохранение их номера в заголовках. Интеграционный
  сценарий принудительно отправляет ошибочное сообщение через partition 2
  и проверяет получение в partition 0 DLQ.

### Организация браузерных проверок

Конфигурация и сценарии находятся в `ui/e2e`; [инструкция запуска](e2e/README.md).
Основной набор сам собирает UI и поднимает preview на 127.0.0.1:4173. Он
проверяет настоящий DOM/CSS и поведение браузера, перехватывая все запросы API
для изоляции данных. Непредусмотренные API-запросы и ошибки JavaScript роняют тест.
Обычные Node/React-тесты и серверная регрессия запускаются отдельно.

Для реального сервера есть `npm --prefix .\ui run test:e2e:live`: проверка входа
без авторизации и отдельный сценарий загрузки Inbox тестовым сотрудником с
проверкой успешного ответа поиска. Для второго нужны PW_USERNAME/PW_PASSWORD.
Отсутствие этих переменных явно отмечается как пропуск, а недоступный сервер
роняет live-набор. Доступность Chromium не зависит от расширения ChatGPT в IDEA.

28 проверок с подготовленными API дополняются отдельной приёмкой с настоящим
backend, описанной ниже. Они не подтверждают фактическую доставку в Telegram.

## Приёмка с настоящим backend от 19.10.2026

Добавлен явный opt-in стенд `InboxBrowserAcceptance`: Spring Boot на случайном
порту, PostgreSQL/Kafka в тестовых контейнерах, настоящий HTTP/JWT/ACL и
production-сборка React. Для каждого сценария и размера экрана создаётся своя
организация с двумя сотрудниками, супервизором и администратором, Workspace,
изолированным Workspace, аккаунтами и диалогами. Рабочая БД не используется.
Команда запуска и пути отчётов — [e2e/README.md](e2e/README.md).

Пройдено **20 из 20** браузерных сценариев, ошибок и пропусков нет:

| Сценарий | Проверено на настольном и мобильном Chromium |
| --- | --- |
| navigation | Прямой вход `/login`, сохранение/чтение фильтра в БД, смена области, история браузера, сброс; запрет сотруднику изменять системный фильтр |
| groups | Создание/переименование/значок/удаление; добавление и удаление membership через UI с чтением результата из БД; запрет чужому владельцу |
| clients | Создание клиента из диалога, отвязка, поиск и привязка существующего; сохранение черновика и проверка связи через API |
| assignments | «Взять / Освободить» сотрудником; назначение супервизором через UI; реальный 403 после переназначения, скрытие редактора и восстановление доступа; действия администратора |
| concurrency | Два независимых браузерных контекста одновременно нажимают «Взять»: один 200 и один 409; membership удаляется после переназначения, повторное добавление запрещено |
| errors | Обрыв запроса поиска и внедрённый 503 сохраняют карточки и допускают повтор; реальные 403 чужого диалога и 404 неизвестного ID скрывают переписку |
| history | 125 сообщений из реальной БД, догрузка без дублей и сохранение прокрутки; черновик сохраняется при работе с меню и повторном выборе диалога |
| isolation | Сотрудник/супервизор не читают недоступный Workspace и не удаляют чужую группу; администратор видит Workspace своей Organization, не читает чужую Organization и не создаёт личные группы |
| transitions | Настоящий ответ сообщения задерживается во время A → B → A, ответ поиска задерживается во время смены Workspace; старые ответы не заменяют текущие данные |
| visibility | Скрытая мобильная переписка не опрашивается, черновик сохраняется; после открытия опрос возобновляется. Проверено и на мобильном устройстве, и при сужении настольного окна |

В успешных операциях ответы API не подменяются. В `errors` намеренно вводятся
обрыв запроса поиска и HTTP 503; в `transitions` задерживаются настоящие ответы
backend. Канал на стенде отключён: сообщения внешнему получателю не отправляются.
Свойства `document` не подменялись. В данном headless Chromium переключение
страниц и сворачивание окна не переводят `document.visibilityState` в `hidden`.
Нативное скрытие вкладки остаётся отдельным непроверенным пунктом; React-тесты
обработчика видимости и проверка мобильного скрытия не выдаются за его замену.

Найдены и исправлены два дефекта:

- Прямое открытие `/login` на Spring Boot возвращало 403: маршрут добавлен
  в публичные страницы SecurityConfig и SPA-forward. Все сценарии стенда
  начинают вход с проверки HTTP 200 этого маршрута.
- При уже достигнутом начале истории отключённый канал давал 409 вместо
  подтверждения конца истории. Теперь после проверки ACL сервер возвращает
  пустой результат с `historyStartReached=true` без команды в Kafka. Новая
  unit-регрессия проверяет отсутствие обращения к платформе; проверка отказа
  доступа также выполняется для завершённой истории.

Повторно пройдены 176 UI-тестов, 28 браузерных сценариев с подготовленными API,
проверка типов Playwright и production build. `MessageServiceTest`: 66 пройдено.
Полный серверный прогон: **619 пройдено**, ошибок и пропусков нет; JVM завершилась
штатно. Отдельный opt-in harness завершился успешно, в его логе — 20 пройденных
браузерных тестов. Временный manifest с учётными данными удалён после прогона.
Скопированы 45 файлов UI; совпадение хешей проверяется с production-сборкой.

получателе. Результаты каждого пункта отмечать после фактической проверки.
