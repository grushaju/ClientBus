# ClientBus — Inbox / «Диалоги»: согласованная UI-спецификация

Статус: концепция согласована; макет не является подключённой к backend реализацией.

## Область работ

- Меняем только UI Inbox/«Диалоги».
- Не меняем глобальную навигацию, App shell, Workspace switcher и остальные разделы.
- Сохраняем существующую переписку справа; добавляем только нужные элементы и раскрываемую панель деталей.
- Перед реализацией сверяем текущие API, модели и права. Не имитируем на рабочем UI действия, для которых нет backend-поддержки.

## Основной экран

### Внутренняя навигация

- **Мои диалоги**
- **Свободные** — диалоги без назначенного Employee; в этом сценарии сотрудник может взять диалог себе.
- **Мои группы** — персональные группы диалогов; необходимость backend-поддержки оценить отдельно.

Не добавлять «Все диалоги» и «Требуют внимания». Фильтры не должны расширять доступ пользователя или смешивать представления.

### Список диалогов

- Поиск и кнопка **Фильтры**; панель фильтров не занимает место постоянно.
- Сортировка списка.
- Карточка: аватар, имя/аккаунт, канал, время последнего сообщения, превью, счётчик непрочитанных.
- Индикатор связи с Client:
  - **Клиент есть** — `ClientAccount.client` связан с Client.
  - **Без клиента** — `ClientAccount` не связан с Client.
- Эти подписи описывают связь сущностей, а не состояние диалога.

### Переписка и детали

- Основная переписка сохраняет текущую структуру.
- Кнопка **Детали** открывает/закрывает дополнительную правую панель и сжимает область переписки.
- Детали: Client (если существует), ClientAccount, канал/подключение и назначенный Employee.
- Для аккаунта без Client панель деталей также должна работать.
- Действия создания/связывания Client и назначения сотрудника показывать только при наличии реальной поддержки.
- После назначения свободный диалог должен исчезнуть из «Свободные» и появиться в «Мои диалоги», если это обеспечено backend-механикой.

### Группы
- Создание группы через `+` рядом с заголовком «Мои группы» или через меню списка.
- Переименование и удаление группы через `⋯` у названия группы.
- Добавление диалога в одну или несколько групп через `⋯` у диалога.
- Уже выбранные группы отмечены в окне добавления.
- Удаление группы не удаляет диалоги и сообщения.
- «Убрать из текущей группы» удаляет только членство диалога в группе.
- Демонстрационное правило: в группы можно добавлять только диалоги, назначенные текущему сотруднику. Для свободного диалога сначала нужно выбрать «Забрать диалог себе».

## Фильтры

1. **Канал**: Telegram, Instagram, WhatsApp, другие каналы; выбор нескольких каналов.
2. **Связь с клиентом**: «Клиент есть», «Без клиента» (и отсутствие ограничения).
3. **Клиентские аккаунты**: независимый поиск по имени, username, телефону и другим доступным атрибутам; множественный выбор. Аккаунты могут принадлежать разным каналам и не обязаны быть связаны с Client. Несколько выбранных аккаунтов объединяются по OR.
4. **Прочтение сообщений**: «Есть непрочитанные», «Только прочитанные» — только если модель достоверно поддерживает это состояние.
5. **Активность**: «Сегодня», «Последние 7 дней», «Последние 30 дней», «Произвольный период».
6. **Сортировка**: «Сначала новые сообщения», «Сначала старые сообщения», «Сначала давно без активности».

Не добавлять другие условия без отдельного согласования. Фильтрация действует внутри текущего представления и никогда не расширяет права доступа.

## Сохранённые фильтры

- Действие **Сохранить фильтр**, ввод названия.
- Личные фильтры отображаются в блоке **Мои фильтры**.
- Личный фильтр может переименовывать, изменять и удалять только владелец/создатель.
- Системные фильтры отображаются отдельно в блоке **Системные фильтры** с пояснением «Управляет администратор».
- Системные фильтры применяются сотрудниками, но редактируются/удаляются и создаются только администратором.
- Изменение системного фильтра для личных целей — сохранить копию как личный фильтр.
- Фильтр хранит условия, выбранные `ClientAccount` и сортировку, а не снимок списка; при открытии применяется к актуальным данным.
- Примеры системных: «Аккаунты без клиента», «Непрочитанные за неделю».
- Примеры личных: «Telegram без клиента», «Давно не было сообщений».
- Создание возможно через `+` возле «Мои фильтры» или «+ Создать фильтр».

## Модель и права фильтров

- `isPrivate`: `1` — личный; `0` — системный.
- `ownerId`: владелец личного фильтра или администратор, управляющий системным.
- Не добавлять `workspaceId`: доступ к фильтрам следует доступным пользователю Workspace; не дублировать эти связи в фильтре.
- Личный фильтр (`isPrivate=1`): доступен/редактируется только `ownerId`.
- Системный фильтр (`isPrivate=0`): виден сотрудникам в рамках доступных Workspace; создавать, редактировать и удалять его может только администратор.
- `ownerId` не даёт сотруднику права редактировать системный фильтр.
- Backend обязан проверять права; API не должен допускать эскалацию через изменение `isPrivate` или `ownerId`.
- Перед изменением схемы проверить существующие сущности, поля, API и авторизацию; не создавать дублирующие поля.

## Существующий контекст модели

- `ClientAccountEntity.client` nullable.
- Внешний аккаунт может существовать без связанного `Client`.
- `ClientAccountService.getOrCreateForInbound` намеренно не создаёт и не назначает `Client` автоматически.
