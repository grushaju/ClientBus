# Синхронизация CRM

`clientbus.crm.sync` в `server/src/main/resources/application.yml` управляет фоновым обновлением привязанных проектов. Настройки связываются с `CrmSyncProperties` и проверяются при запуске. Стандартные профили Spring, внешние YAML и переменные окружения переопределяют значения. Изменения применяются после перезапуска. Индивидуальных переопределений из БД и динамической перезагрузки настроек сейчас нет.

## Выполнение

`CrmSyncCoordinator` формирует задачи независимо от открытых страниц. PostgreSQL хранит расписание в `crm.syncjob`, а `crm.syncconnectionlease` атомарно ограничивает число одновременно выполняемых задач подключения. Планирование и создание таблиц защищены advisory lock. Захват задач использует `FOR UPDATE SKIP LOCKED`; токен и срок блокировки защищают завершение и heartbeat от старого исполнителя.

Очередь хранит только сведения о запуске. `crm.syncstate` остаётся владельцем поколений, курсоров, полноты и областей загрузки. Существующие загрузчики проверяют подключение, версии учётных данных, контекст и часовой пояс перед сохранением. Запросы CRM выполняются вне транзакций БД. Повторное применение страниц использует существующие правила идентификации и обновления объектов.

Сетевой бюджет остаётся общим для CRM и чатов: `clientbus.dikidi.requests-per-second`, `request-burst`, `global-requests-per-second`, `global-request-burst`, `request-parallelism`, `retry-base-ms`, `retry-max-ms`. Таймауты соединения и запроса — `clientbus.crm.connect-timeout-ms`, `request-timeout-ms`. Очередь не создаёт второй HTTP-клиент или отдельную сессию.

Ручные обновления `/projects/{id}/refresh`, первичная загрузка каталога и обновление финансов карточки используют эту же очередь. Одинаковые запросы объединяются по проекту, набору данных и области. Ручной запрос получает `manual-priority`. Инициатор сохраняется отдельно и повторно проверяется загрузчиком; системный запуск не использует пользовательскую сессию и не подставляет администратора. Если принудительный запрос конфликтует с уже запущенным обычным запросом той же области, возвращается `CRM_CONNECTION_BUSY`.

## Наборы данных

| Ключ `datasets` | Что загружается |
|---|---|
| `catalog` | Мастера, услуги, категории, предложения и метаданные проекта одним чтением DIKIDI |
| `clients` | Постраничный справочник клиентов без запросов статистики каждой карточки |
| `client-statistics` | Статистика клиентов: сначала отсутствующая, затем самая старая |
| `appointments` | Записи в настроенном окне вокруг текущей даты проекта |
| `schedules` | Графики наблюдаемых мастеров в настроенном окне |
| `history` | Архив записей проекта от `past-days` дней назад до вчерашнего дня |
| `client-history` | История конкретного клиента по ручному запросу; автоматический обход каждого клиента не создаётся |
| `finance` | Финансовые сведения отдельных записей; автоматический обход по умолчанию выключен |

Новые проекты автоматически не привязываются. Синхронизация работает с явно привязанными проектами. Для календарных данных требуется сохранённый часовой пояс проекта; системный часовой пояс не подставляется.

Графики разбиваются на `chunk-days`, максимум 31 день на область. Внутренние границы привязаны к эпохе, крайние обрезаются по настроенному окну. Журнал DIKIDI читается по одному дню: автоматические окна и ручные периоды записей/истории клиента превращаются в отдельные дневные задачи. Поэтому бюджет в одну страницу не вызывает повторное чтение начала недели. Ранее сохранённые ручные задачи длинных периодов преобразуются при планировании; состояние периода агрегируется из дневных чтений. При смене даты координатор создаёт новые крайние области и отключает вышедшие из окна. Неактивные задачи удаляются через `retired-job-retention`; сами данные CRM при этом не удаляются.

## Параметры

Глобальные параметры: `enabled`, `scheduler-tick`, `planning-interval`, `workers`, `connection-workers`, `manual-priority`, `lease-duration`, `heartbeat-interval`, `retry-initial-delay`, `retry-max-delay`, `retry-multiplier`, `retry-jitter`, `aging-interval`, `retired-job-retention`.

Увеличение ожидания на `aging-interval` даёт задаче дополнительный балл приоритета. Это позволяет старым задачам статистики и истории обгонять новые срочные задачи. Между проектами порядок определяется общей очередью и возрастом ожидания. При изменении параметров все экземпляры сервера должны использовать согласованную конфигурацию.

Параметры набора:

- `enabled` — создание автоматических задач; ручной запуск остаётся доступен.
- `refresh-interval` — пауза после успешного выполнения; для клиентов — после завершения полного прохода.
- `stale-after` — возраст статистики/финансов, после которого объект включается в автоматический обход; также порог свежести соответствующих локальных представлений.
- `batch-size` — число клиентов статистики или финансовых задач при планировании. Статистика DIKIDI допускает 1–5 клиентов.
- `max-pages-per-run`, `max-run-duration` — бюджет постраничного чтения клиентов и записей. Время проверяется между запросами; отдельный запрос ограничен таймаутами адаптера.
- `continuation-delay` — пауза перед продолжением ограниченного выполнения. Справочник клиентов продолжает с сохранённого курсора и признака полноты предыдущих порций. Дневные задачи журнала не переносят курсоры между поколениями; каждый следующий день является самостоятельной задачей.
- `past-days`, `future-days` — календарное окно; история заканчивается вчера независимо от `future-days`. `chunk-days` задаёт размер области графиков; журнал DIKIDI всегда делится по дням.
- `item-retry-delay` — время исключения неудачной пачки статистики из отбора, чтобы она не блокировала остальных клиентов.
- `priority` — базовый приоритет автоматических задач.

При ошибке время последнего успешного обновления сохраняется, а следующая попытка получает экспоненциальную задержку с jitter и настроенным пределом. Ошибка авторизации подключения приостанавливает его очередь до восстановления доступа. Отзыв доступа инициатора завершает его ручную задачу с `ACCESS_DENIED`. Неудачная статистика не меняет `crm.client.statisticsupdatedat`; успешная снимает `statisticsretryat`.

Финансовый обход сначала выбирает ещё не запрошенные записи, затем давно проверявшиеся. Ошибки первых записей не удерживают всю пачку при последующем планировании; время повтора конкретной задачи сохраняется. Объединение ручных запросов сохраняет ранее установленный `force=true` до завершения задачи.

Подтверждённые операции ставят в ту же очередь дневные и точечные дочитывания, включая даты вне автоматического окна. Сохранённые ранее задания из `crm.syncstate` импортируются при планировании. Пустой точечный ответ не завершает задание: оно повторяется до наблюдения записи. `expectedcontext` сохраняет контекст операции; смена подключения, учётных данных, версии контекста или часового пояса отменяет такое чтение до сетевого запроса.

`enabled: false` на уровне `sync` останавливает координатор. Старые polling-компоненты больше не регистрируются как фоновые Spring-компоненты; их прежние настройки не запускают параллельную синхронизацию. Явные ручные обновления при выключенном координаторе сохраняют прежний прямой путь выполнения.

Ограничения конфигурации проверяются до запуска: положительные интервалы, допустимые окна, число работников, размер статистической пачки, heartbeat короче трети lease. Минимальный lease — 90 секунд: адаптер DIKIDI имеет ограниченный многошаговый сетевой сеанс до 75 секунд. Блокировка писателя продлевается между страницами, в том числе перед зеркалированием аватаров.

## Наблюдение

У администратора в «Настройки → CRM», внутри карточки аккаунта под каждым привязанным проектом, есть раскрываемый раздел «Синхронизация CRM»: состояние направлений, ошибки, число задач, время успешного выполнения всех текущих областей и покрытие статистики клиентов. Он загружается по открытию, обновляется по событиям изменения данных и кнопкой.

`GET /api/crm/projects/{id}/sync-overview` возвращает агрегированное состояние, `GET /api/crm/projects/{id}/sync-jobs` — отдельные активные области. Оба требуют обычного доступа к проекту. Время успеха всех задач не означает подтверждённую полноту внешнего источника: её по-прежнему отражают `crm.syncstate` и существующие ответы страниц.

Чаты продолжают использовать механизм синхронизации каналов и общий сетевой ограничитель. Эта очередь управляет CRM-проекциями и не заменяет курсоры доставки сообщений.
