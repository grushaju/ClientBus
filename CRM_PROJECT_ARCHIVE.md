# Отвязка проекта CRM — 12.4.7

07.11.2026 пользователь выбрал сохранение загруженных данных и ручных сопоставлений в архиве. Отвязка освобождает активную привязку Workspace, не удаляя проект из локальной истории.

## Пользовательский сценарий

В настройках CRM Workspace нажмите «Отвязать проект», прочитайте последствия и подтвердите действие. Отмена ничего не меняет. Операция доступна только SUPER_ADMIN своей организации, в том числе для проекта с отключённым обновлением или недоступным аккаунтом. DIKIDI при отвязке не вызывается.

Каталог, CRM-клиенты, графики, визиты, финансовые снимки, ручные связи Client/Employee и их аудит остаются в исходном Workspace. Архив виден в настройках и списке проектов CRM. Сохранённый каталог и связи сотрудников доступны для просмотра; элементы изменения связей заблокированы. Экраны клиентов, расписания и визитов по-прежнему относятся к 12.5; их локальные read API сохраняют доступ к архиву с прежней проверкой Organization/Workspace.

В освободившийся Workspace можно подключить другой проект DIKIDI. Кнопка «Выключить обновление» сохраняет прежнее поведение: останавливает чтение, но продолжает занимать активную привязку.

Чтобы восстановить архив, освободите активную привязку, выберите аккаунт, введите прежний внешний ID и проверьте проект. После явного подтверждения «Восстановить проект» возобновляется обновление прежнего проекта с теми же локальными UUID, историей и сопоставлениями. Аккаунт можно выбрать другой. Архив нельзя переносить в другой Workspace: это сохраняет прежнюю границу доступа к истории. Если часовой пояс при восстановлении не указан, сохраняется прежний.

Архив сохраняет ссылки на исходные Workspace и аккаунт CRM, поэтому их удаление остаётся заблокированным. Для смены аккаунта архива сначала восстановите проект и смените аккаунт в его настройках. Сами клиенты/сотрудники ClientBus не удаляются и не меняются при отвязке. Если их позже удаляет другой прикладной сценарий, прежняя логика снимает CRM-связь с аудитом `TARGET_DELETED`; архив не превращает удаление core-объектов в каскадное удаление истории.

## Сервер и хранение

- `POST /api/crm/projects/{id}/detach?expectedVersion=...` возвращает `CrmProjectDto` с `archived=true`, `enabled=false` и новой версией. Пропущенная/отрицательная версия — 400, устаревшая — `CRM_VERSION_CONFLICT`, повторная операция над текущей версией архива — `CRM_PROJECT_ARCHIVED`.
- Порядок блокировок: Workspace → Connection → Project; у workers — Connection → Project. После ожидания повторяются проверки администратора, доступа к Workspace и версии.
- `contextVersion` увеличивается; все syncstate поколений и claims проекта инвалидируются в той же транзакции. Поздние CATALOG, CLIENTS, SCHEDULE, APPOINTMENTS/CLIENT_HISTORY и FINANCE не могут опубликовать результат даже после восстановления проекта.
- `crm.project.archived` — non-null boolean с default false для существующих строк. Check запрещает `archived=true, enabled=true`. Индекс `uqprojectdikidiworkspace` уникален по workspaceid только при `provider='DIKIDI' AND archived=false`. Проверенный прежний индекс заменяется атомарно под блокировкой таблицы; неожиданный индекс не принимается. Миграции Flyway не добавляются: действует существующий bootstrap после Hibernate update.
- Сохраняются FK Workspace/Connection и уникальность Organization/provider/externalId. Восстановление принимает дополнительное `expectedArchiveVersion` в `BindCrmProjectRequest`; обычный или запоздавший bind без этой версии не восстанавливает архив. Версия фиксируется на UI при проверке проекта, а не подменяется новым GET перед нажатием подтверждения.
- Изменения настроек/аккаунта проекта и ручных связей проверяют архив после блокировки проекта. Refresh отклоняется для выключенного проекта, workers дополнительно проверяют archived и полный контекст. Чтение архива не расширяет доступ к другим Workspace.
- После commit публикуется `crm.invalidated`. GET и ответы всех изменений проекта проходят общую проверку version/contextVersion: поздний ответ отвязки не заменяет более новое восстановление, а поздний ответ восстановления — более новую отвязку. Максимальная наблюдённая версия запоминается и до первого локального изменения. Старый/пустой GET после сохранения не возвращает прежнюю привязку; версия подтверждения не меняется в фоне. Если ответ изменения уже устарел, UI сообщает, что показана актуальная версия, вместо ложного сообщения об отвязке/подключении. При отзыве доступа данные и наблюдённые версии очищаются, поздний ответ не применяется.

## Проверка

Полный прогон CRM/DIKIDI: 266 тестов без ошибок и пропусков, включая 154 PostgreSQL/Testcontainers сценария `CrmFoundationIntegrationTest`. После последних уточнений повторены 30 тестов архивирования и HTTP-контрактов, включая дополнительную регрессию ранее начатого bind, чей inspect завершился после отвязки, и отрицательную версию восстановления. Сохранность всех CRM-таблиц сравнивается до/после операции; проверены ссылки на core Client/Employee, финансовый снимок, повторное подключение и частичный уникальный индекс. Логи: `server/target/crm-project-detach-all.log`, `server/target/crm-project-detach-final.log`.

UI: все 442 теста прошли; 47 React/API-проверок CRM включают сохранение подтверждённой версии архива, поздний ответ после отзыва доступа, пустые/устаревшие GET и неизменяемые сопоставления. Четыре регрессии ревью проверяют обе последовательности поздних ответов отвязки/восстановления при ошибке следующего GET, расхождение версий начальных списков Organization/Workspace без смешивания пространств и старый GET до первого локального изменения. Лог полного прогона: `ui/node_modules/.cache/crm-project-version-ui-final.log`.

Playwright: 20 сценариев desktop/mobile прошли с API-фикстурами, включая отмену, архивный каталог и неизменяемые связи, восстановление прежнего проекта и подключение другого. После последнего уточнения сравнения версий повторены четыре сценария отвязки/восстановления desktop/mobile. Типы e2e и production build успешны. `mvn -o process-resources` выполнен; SHA-256 всех 46 файлов UI совпали с серверными копиями. Лог ресурсов: `server/target/crm-project-version-resources.log`.

Новые живые запросы DIKIDI и изменения рабочих данных не выполнялись. Живая приёмка предыдущего чтения сохраняет границы из CRM_ACCEPTANCE.md.

Для появления новой операции и bootstrap схемы нужно перезапустить сервер после сборки ресурсов UI.
