Этап 11 — Notification: общая система обновлений UI и персональных уведомлений
Архитектура и план реализации от 19.10.2026. BE — backend.
Пункты ниже описывают целевую реализацию; результаты выполнения фиксируются отдельно.

ЦЕЛЬ И ОБЪЁМ

UI получает изменения из других сессий и от фоновых обработчиков без ручного обновления страницы. После разрыва соединения UI восстанавливает актуальное состояние через REST. Значимые персональные уведомления доступны после закрытия браузера и повторного входа в приложение.

В этап входят:
    — общий поток обновлений для Inbox, сообщений, клиентов, каналов, сотрудников, Workspace и текущих прав доступа;
    — базовый персональный центр: список, непрочитанный счётчик, прочтение одного/всех уведомлений, переход к объекту;
    — надёжная публикация изменений из HTTP- и Kafka-обработчиков;
    — согласование UI после reconnect и ограниченная миграция History Sync в сохраняемую операцию;
    — эксплуатационные ограничения, метрики, регрессия и приёмка.

За пределами этапа: email/SMS, Web Push при закрытом браузере, desktop permissions, presence/typing, конструктор правил и сложных предпочтений, универсальный job framework, общий журнал replay событий для браузера. Звуковые уведомления и межвкладочная координация звука не требуются для готовности базовой версии.

АРХИТЕКТУРНОЕ РЕШЕНИЕ

1. Разделить четыре модели с разными обязанностями.
    Внутреннее событие/команда — обработка в backend; существующие Kafka DTO не раскрываются браузеру автоматически.
    UI invalidation — короткий сигнал, что ресурс нужно перечитать через REST. Не содержит текста сообщений, вложений или полного DTO сущности.
    Персональное уведомление — сохранённая запись для конкретного сотрудника с собственным состоянием прочтения.
    Операция History Sync — сохраняемый ресурс со статусом и результатом; уведомление об операции не заменяет её состояние.

2. Основной поток изменений:
    HTTP request / Kafka consumer
        → одна PostgreSQL-транзакция: бизнес-изменение + необходимые персональные уведомления + outbox
        → outbox relay с повторными попытками публикации
        → отдельный Kafka topic clientbus.ui.invalidations.v1
        → gateway каждого экземпляра приложения
        → SSE
        → глобальный UI provider
        → объединённое перечитывание затронутых REST-ресурсов.
    Для принятой команды History Sync та же транзакция сохраняет operation и outbox-команду в существующий Kafka history topic.
    Перенос всех остальных существующих Kafka-команд на outbox не является условием этапа 11; охват изменений фиксируется каталогом событий.

3. Transport: SSE поверх существующего Spring MVC/SseEmitter; в браузере — streaming fetch с Authorization: Bearer и AbortController.
    Запись данных остаётся через существующие REST-команды. JWT не передаётся в URL. Перевод приложения на WebFlux, WebSocket или новый микросервис не требуется.
    Клиент использует проверенный SSE parser либо отдельный протестированный parser: границы UTF-8/chunks, CRLF, multiline data, комментарии, завершение потока, ограничения размера.
    Для SSE проверяются async dispatch Spring Security, очистка соединений, flush, отключение proxy buffering/cache, heartbeat и тайм-ауты.

4. Гарантии фиксируются по границам.
    Бизнес-данные, персональное уведомление и соответствующая запись outbox сохраняются атомарно. Rollback не создаёт видимого уведомления или события.
    Outbox → Kafka: публикация с повторными попытками, возможны дубликаты. Отметка published ставится только после подтверждения Kafka.
    SSE: оперативные сигналы без гарантии обработки каждого события браузером. Подтверждение записи в сокет не равно получению, отображению или прочтению.
    UI: актуальное состояние восстанавливается через REST; повтор и перестановка invalidation не должны менять бизнес-состояние.
    Сохранённые уведомления доступны через REST независимо от состояния SSE до очистки по retention, с учётом текущих прав.
    Exactly-once до браузера, порядок между разными сущностями и непрерывный browser replay не обещаются. Kafka offset/outbox ID/UUID не используются как браузерный курсор.

5. Outbox и идемпотентность.
    Запись outbox содержит стабильный eventId, назначение публикации, минимальный payload, createdAt, publishedAt, attempts и данные очередной попытки.
    Несколько relay безопасно распределяют работу через короткие DB claims/lease; сетевое ожидание не удерживает долгую бизнес-транзакцию. Crash до/после Kafka ack допускает повтор.
    Персональные записи защищены UNIQUE(recipientEmployeeId, deduplicationKey). Ключ обозначает бизнес-возникновение события, а не новый UUID каждой попытки Kafka-публикации.
    Повторная обработка одного входящего сообщения/статуса не создаёт новые уведомления. Для отдельной повторной попытки отправки явно определяется новая бизнес-операция.
    Outbox очищается только по правилам публикации/retention. Отдельный долговечный UI event journal в первой версии отсутствует.

6. Доставка между экземплярами.
    Каждый gateway имеет свою consumer group выделенного UI topic; группа создаётся на экземпляр, а не на пользователя, Workspace или SSE-соединение.
    Все gateway получают invalidation и доставляют разрешённые сигналы своим локальным соединениям. Redis и sticky sessions для этого механизма не требуются.
    Идентификаторы экземпляров, ограничение числа групп и очистка групп выведенных экземпляров входят в эксплуатационную конфигурацию.
    Gateway регистрирует соединение и отправляет stream.ready только после готовности Kafka-подписчика. Потеря/восстановление подписки требует reconnect/resync клиентов.
    Живой SSE heartbeat сам по себе не подтверждает исправность Kafka/outbox. Состояние pipeline и возраст outbox наблюдаются отдельно; периодическая REST-сверка страхует пропущенные сигналы.
    Kafka consumer не выполняет блокирующую отправку в сокеты: ограниченные очереди и executor, объединение одинаковых invalidation. Переполнение вызывает resync/закрытие соединения, а не рост памяти.

7. Routing и security.
    Backend вычисляет получателей. Organization, Workspace, роль, назначение диалога и принадлежность личных объектов проверяются на сервере.
    Общая authorization policy принимает явный subject; её используют REST и gateway. CurrentUserService/SecurityContextHolder нельзя считать доступным в Kafka/executor-потоке.
    Подписка и очередь соединения не являются бессрочным разрешением: перед отправкой проверяется действующий доступ. Кэш прав имеет явную инвалидацию при изменениях ACL.
    При переназначении прежний сотрудник получает минимальный access.invalidated без текста сообщений и новых приватных данных. UI очищает недоступные данные и перечитывает разрешённые разделы.
    Изменение состава Workspace, роли, организации или блокировка пользователя обновляют/закрывают существующие соединения. При истечении JWT соединение закрывается; бесконечный retry с тем же токеном запрещён.
    При logout или смене пользователя UI закрывает stream, отменяет запросы и очищает данные/очереди предыдущего пользователя. В первой версии нет требования нового refresh-token механизма.
    REST списка/счётчика/прочтения уведомлений и статуса операции повторно проверяет текущие права. Недоступные цели исключаются из выдачи и непрочитанного счётчика; сохранённое preview не обходит ACL.

8. UI recovery: subscribe → ready → REST reconciliation.
    После stream.ready UI перечитывает активные представления и summary уведомлений. До завершения сверки данные не считаются восстановленными.
    Invalidation помечает соответствующую query/resource как dirty. События объединяются; один event не обязан создавать отдельный HTTP-запрос.
    Если событие пришло во время запроса, dirty сохраняется и после завершения выполняется повторное чтение. При ошибке dirty не теряется; применяются retry/backoff.
    Повторная сверка нужна после reconnect, возвращения вкладки, смены Workspace и восстановления Kafka pipeline. Периодическая редкая сверка активных данных остаётся страховкой; при отказе SSE включается ограниченный polling.
    Скрытая вкладка не опрашивает переписку; накопленные изменения согласуются при возвращении. Новые сообщения дочитываются до прежней границы без пропуска страниц.
    Сохраняются generation guards, защита A → B → A, локальные версии отправки/retry, черновик, прокрутка, фильтры, сортировка и membership. Произвольные push DTO не подменяют состояние.
    Подписки неактивных экранов не вызывают полный refetch всего приложения. При их открытии выполняется обычная REST-загрузка.

9. Центр уведомлений: ограниченный продуктовый объём.
    Сохраняются: назначение диалога адресату; окончательная ошибка отправки ответственному сотруднику; канал требует действия — доступным руководителям/администратору; значимый итог явно запущенной длительной операции её инициатору.
    При отсутствии ответственного у ошибки отправки получатели определяются каталогом сценариев по текущим правам руководителей. Повторные сигналы одной ошибки не создают пачку записей.
    Новые сообщения прежде всего обновляют Inbox. Для каждого сообщения каждому руководителю запись в центре не создаётся.
    Импорт истории, периодическая фоновая синхронизация и подгрузка очередной страницы не создают персональные уведомления или всплывающие сообщения об успехе. Ошибка обычной подгрузки показывается в её контексте.
    Минимальная модель: id, recipientEmployeeId, organizationId, workspaceId при наличии, type, targetType/targetId, безопасные templateArgs, createdAt, readAt, deduplicationKey.
    Контент формируется из известных типов и безопасно отображаемых аргументов; HTML и произвольные URL из источника не исполняются. Ссылка строится UI из типизированной цели и проверяется REST при переходе.
    Список имеет стабильную keyset-пагинацию по (createdAt, id). Это пагинация записей, а не курсор доставки SSE. Счётчик вычисляется по доступным непрочитанным записям; отдельный счётчик-проекция пока не нужен.
    Прочтение одного/всех идемпотентно и синхронизируется между сессиями через notifications.invalidated. «Прочитать все» использует один DB snapshot доступных записей; уведомления, зафиксированные позднее, остаются непрочитанными.
    UI: кнопка и счётчик в AppLayout, список всех/непрочитанных, пагинация, loading/empty/error/retry, клавиатура, доступные подписи, мобильное представление, корректный переход между Workspace.
    Всплывающее сообщение — только для новой значимой live-записи после первоначальной сверки; дедупликация по notificationId. Reconnect/загрузка старых страниц не воспроизводят старые всплывающие сообщения. Звук отключён.
    Удаление/архивирование пользователем и гибкие настройки типов не входят в базовый API. Retention уведомлений и outbox настраивается отдельно.

10. Контракты первой версии.
    Browser event: eventId, schemaVersion, type, occurredAt; workspaceId и resource(kind, id) только при необходимости и разрешённом доступе; correlationId при наличии.
    Пример: messages.invalidated для разрешённого conversationId. Другие семейства: inbox, clients, channels, workspace, identity/access, notifications, history-operation.
    Внутренние routing-поля/получатели и Kafka-команды в browser event не переносятся. occurredAt служит диагностике, а не определяет порядок или полноту доставки.
    Control events: stream.ready, stream.heartbeat, stream.resync-required. Access invalidation минимальна и не раскрывает недоступную сущность.
    Неизвестный type не ломает UI: ограниченная общая сверка и диагностика. Несовместимая версия переводит клиент на безопасный fallback, без бесконечных reconnect.
    GET /api/events — SSE для текущего пользователя, с разрешённой областью текущего Workspace; персональные notification/access-сигналы не ограничены выбранным Workspace.
    GET /api/notifications — список с unreadOnly, limit и pageCursor; GET /api/notifications/summary — доступный unreadCount.
    PUT /api/notifications/{id}/read и PUT /api/notifications/read-all — идемпотентное прочтение.
    POST /api/conversations/{id}/history-sync — принять ограниченную операцию и вернуть 202 с operationId; GET /api/history-sync-operations/{id} — актуальный статус/результат.
    Это целевые endpoints: точные DTO/OpenAPI и совместимость с текущим sync-history API фиксируются в 11.2 до изменения UI.

11. History Sync — отдельная ограниченная миграция.
    Текущее ожидание Kafka-результата в process-local CompletableFuture заменяется сохраняемой history operation; ответ не должен зависеть от экземпляра сервера или открытого HTTP-запроса.
    Принимающая транзакция сохраняет operation и outbox-команду, затем немедленно возвращает 202. Ждать выполнения команды внутри этой транзакции запрещено.
    Состояния: PENDING, RUNNING, SUCCEEDED, FAILED. Сохраняются operationId, инициатор, conversationId, входной cursor/limit, request deduplication key, timestamps, lease/deadline, безопасная ошибка и результат страницы.
    Повтор POST с тем же ключом не запускает новую операцию; повтор Kafka-команды/результата безопасен. Протухшие операции получают определённый terminal outcome, а не остаются RUNNING бессрочно.
    SUCCEEDED фиксируется только после сохранения импортированных сообщений и historyStartReached; изменение статуса и его UI invalidation атомарны. Ошибки, исчерпание повторов и DLQ согласуются со статусом операции.
    UI ожидает статус через invalidation + GET, с polling при деградации транспорта; после reload может восстановить незавершённую подгрузку. Уже сохранённая история читается без внешнего канала, с прежними ACL.
    Origin LIVE/HISTORY_IMPORT/SYNC передаётся явно в путях обработки; давность occurredAt не используется для подавления уведомлений. Подавление применяется ко всем импортным путям, включая Recent Chats Sync.
    Существующие sync run/lease механизмы Recent Chats переиспользуются по смыслу; универсальная система задач, отмена внешнего запроса и расписания в этот этап не включаются.

ПЛАН РЕАЛИЗАЦИИ

11.1 — Семантика, каталог сценариев и гарантии
    11.1.1. Зафиксировать для каждого сценария: источник, бизнес-изменение, затронутые REST-ресурсы, получателей, необходимость персональной записи, UX и origin.
    11.1.2. Согласовать матрицу обычного сотрудника, supervisor и SUPER_ADMIN; личные и Workspace-области.
    11.1.3. Утвердить описанные выше границы SSE/REST/outbox/уведомлений/history operations и критерии приёмки.
    Результат: однозначный каталог событий и получателей; никаких скрытых обязательств exactly-once/replay.

11.2 — Контракты, модель данных и REST API
    11.2.1. Описать отдельно внутренние события, browser envelope, notification DTO и history-operation DTO в OpenAPI/общих типах.
    11.2.2. Подготовить миграции outbox, персональных уведомлений и history operations: уникальности, индексы, FK, lease и правила очистки.
    11.2.3. Определить дедупликацию, snapshot прочтения всех, pagination, безопасные ошибки и совместимость нового history API со старым UI.
    Результат: проверяемые контракты и миграции без автоматического раскрытия внутренних Kafka payload.

11.3 — Общая authorization policy и маршрутизация
    11.3.1. Выделить policy с явным subject, сохранив текущие REST ACL; использовать её для gateway, центра и операций.
    11.3.2. Реализовать определение аудитории, минимальное оповещение прежнего ответственного и смену прав открытого соединения.
    11.3.3. Закрепить тестами изоляцию Organization/Workspace, личные объекты, блокировку, отзыв доступа и истечение JWT.
    Результат: единые правила доступа в HTTP, фоновых потоках и при повторном чтении сохранённых записей.

11.4 — Минимальный SSE gateway и клиент транспорта
    11.4.1. Добавить выделенный UI topic, подписку gateway, registry локальных соединений, handshake, heartbeat и корректное завершение.
    11.4.2. Добавить streaming fetch/parser, авторизацию, отмену, bounded queue/executor, proxy/security async configuration.
    11.4.3. Проверить ready только при рабочем подписчике, потерю pipeline, несколько соединений и очистку ресурсов.
    Результат: проверенный транспорт; heartbeat не маскирует отказ внутренней доставки.

11.5 — Первый вертикальный E2E и надёжная публикация
    11.5.1. Реализовать минимальный outbox/relay и событие входящего live-сообщения после сохранения БД.
    11.5.2. Подключить минимальный глобальный provider и обновление разрешённых Inbox/переписки через REST.
    11.5.3. Выполнить настоящий Kafka/PostgreSQL/SSE/browser E2E: две разрешённые сессии, запрещённая сессия, rollback, повтор и reconnect.
    Результат: работающая вертикаль до подключения всех типов событий и полного центра уведомлений.

11.6 — Глобальный UI client и reconciliation
    11.6.1. Разместить provider на уровне authenticated AppLayout; корректно обрабатывать login/logout, смену пользователя и Workspace.
    11.6.2. Добавить подписки ресурсов, coalescing/dirty во время REST-запроса, обработку ошибки и защиту поздних ответов.
    11.6.3. Сохранить поведение Inbox этапа 10: прокрутку, черновики, группы/фильтры, собственные команды, сообщения и старые статусы.
    Результат: общий механизм обновлений без переписывания бизнес-состояния на произвольные push DTO.

11.7 — Reconnect, деградация, ограничения и несколько экземпляров
    11.7.1. Реализовать backoff с jitter, ready→resync, возврат вкладки, редкую контрольную сверку и ограниченный fallback polling.
    11.7.2. Проверить consumer group на экземпляр, падение/перезапуск relay/gateway/Kafka, rebalance и переполнение очереди.
    11.7.3. Установить конфигурируемые пределы соединений/очередей/payload/refetch, cleanup и управление lifecycle consumer groups.
    Результат: восстанавливается состояние; дубликаты безопасны; память, потоки и REST-нагрузка ограничены.

11.8 — Персональный центр уведомлений BE + UI

КРИТЕРИИ ПРИЁМКИ

    — Изменения из HTTP и Kafka видны другим разрешённым сессиям; недоступные организации, Workspace, диалоги и личные объекты не раскрываются.
    — Rollback не даёт phantom event/notification; crash relay до/после Kafka ack не теряет сохранённое уведомление и не создаёт его дубль.
    — Reconnect, отказ Kafka при живом HTTP, restart сервера, rebalance, потеря вкладкой видимости и смена Workspace приводят к REST-сверке.
    — Событие во время REST-загрузки/ошибки не теряет dirty; перестановка/повтор не откатывают статусы и не возвращают закрытые данные.
    — Работают две сессии одного пользователя, два разных сотрудника, supervisor и SUPER_ADMIN; проверены два gateway с отдельными группами.
    — Отзыв доступа очищает активный UI и центр/счётчик; JWT expiry и logout завершают stream и старые запросы.
    — Центр сохраняет записи после перезапуска/reload, корректно читает одну/все, переживает одновременный приход новых записей и переход к удалённой/недоступной цели.
    — History Sync завершается/ошибается с сохраняемым статусом после смены экземпляра; импорт не создаёт notification storm; обычная пагинация истории не спамит центр.
    — Медленный клиент/массовый импорт не блокирует Kafka consumer, не создаёт неограниченные очереди и не вызывает запрос на каждый event.
    — Определён воспроизводимый нагрузочный профиль и измерены p95 задержки, количество REST-запросов и ресурсы. Численные SLO/лимиты фиксируются до нагрузочной приёмки, без заявления неподтверждённой производительности.
    — Пройдена регрессия Inbox: ACL, сообщения/доставка/retry, история, группы, фильтры, прокрутка, черновик и защита A → B → A.

ОСНОВАНИЯ РЕВЬЮ

    Сохранено из исходного предложения: разделение событий/уведомлений, серверный ACL, HTTP+Kafka источники, outbox для надёжной публикации, ранний E2E и сохранение поведения Inbox.
    Убрано из обязательной первой версии: общий replay-журнал/курсор браузера, версии всех агрегатов, exactly-once до UI, новая инфраструктура Redis/WebFlux/микросервис, сложные preferences и универсальная система jobs.
    Уточнено: outbox не заменяет хранилище уведомлений; SSE не является источником бизнес-состояния; операция History Sync не является уведомлением; базовый центр явно входит в объём, а не подразумевается выбором транспорта.
