ЦЕЛЬ И ОБЪЁМ

UI получает изменения из других сессий и от фоновых обработчиков без ручного обновления страницы. После разрыва соединения UI восстанавливает актуальное состояние через REST. Значимые персональные уведомления доступны после закрытия браузера и повторного входа в приложение.

В этап входят:
    — общий поток обновлений для Inbox, сообщений, клиентов, каналов, сотрудников, Workspace и текущих прав доступа;
    — базовый персональный центр: список, непрочитанный счётчик, прочтение одного/всех уведомлений, переход к объекту;
    — общая для web/native модель уведомлений и BE-основа мобильной доставки: регистрации установок, задания доставки и интерфейс push-провайдера;
    — надёжная публикация изменений из HTTP- и Kafka-обработчиков;
    — согласование UI после reconnect и ограниченная миграция History Sync в сохраняемую операцию;
    — эксплуатационные ограничения, метрики, регрессия и приёмка.

За пределами этапа: email/SMS, Web Push при закрытом браузере, desktop permissions, presence/typing, конструктор правил и сложных предпочтений, универсальный job framework, общий журнал replay событий для браузера. Звуковые уведомления и межвкладочная координация звука не требуются для готовности базовой версии.
Native mobile push отличается от Web Push и предусмотрен архитектурой ниже. Разработка самого мобильного приложения, подключение production FCM/APNs и приёмка реальных устройств выполняются отдельной интеграцией после выбора мобильных платформ; без неё мобильная push-доставка не объявляется готовой.

АРХИТЕКТУРНОЕ РЕШЕНИЕ

1. Разделить пять моделей с разными обязанностями.
    Внутреннее событие/команда — обработка в backend; существующие Kafka DTO не раскрываются браузеру автоматически.
    UI invalidation — короткий сигнал, что ресурс нужно перечитать через REST. Не содержит текста сообщений, вложений или полного DTO сущности.
    Персональное уведомление — сохранённая запись для конкретного сотрудника с собственным состоянием прочтения.
    Операция History Sync — сохраняемый ресурс со статусом и результатом; уведомление об операции не заменяет её состояние.
    Delivery — отдельное сохраняемое задание отправить одно уведомление по выбранному каналу на конкретную регистрацию устройства. Статус delivery не является состоянием прочтения уведомления.
    Все реализации каналов, включая Telegram, используются через существующий ChannelConnectorRegistry/IChannelConnector. Notification опирается на общие доменные ресурсы и результаты; отдельных Telegram scopes, capabilities, прав или owner-routing не добавляет. Внутренние callbacks/auth-step конкретной платформы не расширяют общий Notification-контракт.

2. Основной поток изменений:
    HTTP request / Kafka consumer
        → одна PostgreSQL-транзакция: бизнес-изменение + необходимые персональные уведомления + outbox
        → outbox relay с повторными попытками публикации
        → отдельный Kafka topic clientbus.ui.invalidations.v1
        → gateway каждого экземпляра приложения
        → SSE
        → глобальный UI provider
        → объединённое перечитывание затронутых REST-ресурсов.
    Для принятой команды History Sync та же транзакция сохраняет operation и outbox-команду в существующий Kafka history topic.
    Для разрешённых mobile-push сценариев та же транзакция создаёт notificationdelivery для активных регистраций адресата. Отдельный push worker распределяет эти задания через DB lease и вызывает PushProvider → FCM/APNs → ОС устройства. Это самостоятельная очередь работ; каждый SSE gateway не отправляет push из своей broadcast consumer group.
    Перенос всех остальных существующих Kafka-команд на outbox не является условием этапа 11; охват изменений фиксируется каталогом событий.

3. Realtime transport: SSE поверх существующего Spring MVC/SseEmitter; в браузере — streaming fetch с Authorization: Bearer и AbortController.
    Запись данных остаётся через существующие REST-команды. JWT не передаётся в URL. Перевод приложения на WebFlux, WebSocket или новый микросервис не требуется.
    Клиент использует проверенный SSE parser либо отдельный протестированный parser: границы UTF-8/chunks, CRLF, multiline data, комментарии, завершение потока, ограничения размера.
    Для SSE проверяются async dispatch Spring Security, очистка соединений, flush, отключение proxy buffering/cache, heartbeat и тайм-ауты.
    Native-клиент использует тот же публичный SSE/REST контракт в foreground своим HTTP-клиентом. Для background/suspended/terminated состояния применяется системная push-доставка; постоянное SSE/WS-соединение не считается фоновым механизмом.

4. Гарантии фиксируются по границам.
    Бизнес-данные, персональное уведомление и соответствующая запись outbox сохраняются атомарно. Rollback не создаёт видимого уведомления или события.
    Outbox → Kafka: публикация с повторными попытками, возможны дубликаты. Отметка published ставится только после подтверждения Kafka.
    SSE: оперативные сигналы без гарантии обработки каждого события браузером. Подтверждение записи в сокет не равно получению, отображению или прочтению.
    UI: актуальное состояние восстанавливается через REST; повтор и перестановка invalidation не должны менять бизнес-состояние.
    Сохранённые уведомления доступны через REST независимо от состояния SSE до очистки по retention, с учётом текущих прав.
    Для push состояние PROVIDER_ACCEPTED означает принятие провайдером, а не доставку, показ или прочтение. Возможны задержки, повторы и потеря; открытие приложения всегда вызывает REST-сверку независимо от наличия push. Silent/data-only push не является гарантированным механизмом пробуждения или синхронизации.
    Exactly-once до браузера, порядок между разными сущностями и непрерывный browser replay не обещаются. Kafka offset/outbox ID/UUID не используются как браузерный курсор.

5. Outbox и идемпотентность.
    Запись outbox содержит стабильный eventId, назначение публикации, минимальный payload, createdAt, publishedAt, attempts и данные очередной попытки.
    Несколько relay безопасно распределяют работу через короткие DB claims/lease; сетевое ожидание не удерживает долгую бизнес-транзакцию. Crash до/после Kafka ack допускает повтор.
    Каждый claim выдаёт монотонный claimVersion; запись результата допустима только при совпадении claimVersion и ожидаемого состояния. Истёкший lease допускает нового владельца, но не даёт старому worker перезаписать его результат. Этот же протокол применяется к delivery и history operations; он не устраняет возможный повтор внешнего вызова.
    Персональные записи защищены UNIQUE(recipientEmployeeId, deduplicationKey). Ключ обозначает бизнес-возникновение события, а не новый UUID каждой попытки Kafka-публикации.
    Дополнительно notification occurrence сохраняет первоначальную аудиторию, включая пустую; повтор использует это решение. Повтор LIVE после A→B либо null→B не создаёт новую запись для B. HISTORY_IMPORT/SYNC не фиксирует решение за ещё не обработанное LIVE-возникновение. Occurrence/аудитория сохраняются не меньше поддерживаемого окна повторов независимо от очистки центра; точная модель определяется в 11.2. Основание: R01.
    Повторная обработка одного входящего сообщения/статуса не создаёт новые уведомления. Для отдельной повторной попытки отправки явно определяется новая бизнес-операция.
    SendAttemptId проходит outbound-команду, connector и результат; ручной retry создаёт новую попытку, технический сохраняет прежнюю. Статус обновляется условно для соответствующей попытки: поздний FAILED/SENT не меняет новую и не создаёт для неё N3. Callback без attemptId требует привязки к внешней отправке и безопасного поведения при неоднозначности; одного messageId недостаточно. Реализуется до включения N3; claimVersion push delivery не заменяет эту идентичность. Основание: R02.
    Конфликт deduplicationKey — штатный no-op через INSERT ON CONFLICT, а не перехват constraint exception в уже rollback-only транзакции. Delivery intents создаются при первой вставке уведомления для снимка активных регистраций; повтор источника не отправляет старое уведомление на устройства, зарегистрированные позднее.
    Очистка центра не стирает факт уже созданного уведомления: компактный notificationdedup сохраняет recipient/key независимо от notification row не меньше поддерживаемого окна повторов источника. Окна Kafka retry/replay, idempotency и retention согласуются в 11.2. Повторы старше поддерживаемого окна не создают новые пользовательские эффекты; административный replay выполняется с явным подавлением оповещений.
    Сохранение сообщения и право создать LIVE-уведомление дедуплицируются отдельно. Если HISTORY_IMPORT записал сообщение раньше LIVE-события, наличие сообщения в БД не подавляет единственное разрешённое LIVE-уведомление. Повтор LIVE после LIVE или импорта не создаёт второе уведомление; импорт сам по себе его не создаёт.
    Outbox очищается только по правилам публикации/retention. Отдельный долговечный UI event journal в первой версии отсутствует.
    Постоянная ошибка payload/публикации переводит outbox в наблюдаемый карантин без блокировки других записей и без ложного published. Временный/неоднозначный сетевой отказ повторяется с backoff и тем же eventId. Для ручного повтора сохраняется идентичность; terminal state связанной операции проверяется заново. Невозможность публикации history-команды согласуется с deadline/FAILED операции, UI invalidation восстанавливается REST. Состояния, классификация ошибок и процедура повтора фиксируются в 11.2, relay/метрики — в 11.5. Основание: R07.

6. Доставка между экземплярами.
    Каждый gateway имеет свою consumer group выделенного UI topic; группа создаётся на экземпляр, а не на пользователя, Workspace или SSE-соединение.
    Все gateway получают invalidation и доставляют разрешённые сигналы своим локальным соединениям. Redis и sticky sessions для этого механизма не требуются.
    Идентификаторы экземпляров, ограничение числа групп и очистка групп выведенных экземпляров входят в эксплуатационную конфигурацию.
    Gateway регистрирует соединение и отправляет stream.ready только после готовности Kafka-подписчика. Потеря/восстановление подписки требует reconnect/resync клиентов.
    Живой SSE heartbeat сам по себе не подтверждает исправность Kafka/outbox. Состояние pipeline и возраст outbox наблюдаются отдельно; периодическая REST-сверка страхует пропущенные сигналы.
    Kafka consumer не выполняет блокирующую отправку в сокеты: ограниченные очереди и executor, объединение одинаковых invalidation. Переполнение вызывает resync/закрытие соединения, а не рост памяти.

7. Routing и security.
    Backend вычисляет получателей. Organization, Workspace, роль, назначение диалога и принадлежность личных объектов проверяются на сервере.
    Общая authorization policy принимает явный subject; её используют REST и gateway. CurrentUserService/SecurityContextHolder нельзя считать доступным в Kafka/executor-потоке.
    Подписка и очередь соединения не являются бессрочным разрешением. В первой версии перед чувствительной выдачей/сигналом и push проверяются текущие права по БД, с допустимыми пакетными запросами и вне Kafka consumer socket loop. Задержанная Kafka-инвалидация кэша не подтверждает текущий ACL; отказ policy/БД не разрешает отправку из старого кэша. Оптимизация через кэш требует отдельного протокола подтверждения актуальности. Уже отправленные данные нельзя отозвать; гонка после проверки имеет эту границу. Основание: R03.
    При переназначении прежний сотрудник получает минимальный access.invalidated без текста сообщений и новых приватных данных. UI очищает недоступные данные и перечитывает разрешённые разделы.
    Для удаления объекта, удаления membership и смены ACL нельзя требовать существования/доступности удалённой сущности для отправки сигнала очистки. В транзакции сохраняется минимальная прежняя область/аудитория; разрешённым участникам посылается invalidation списка/доступа без закрытых object-данных. Удаление также инвалидирует центр/summary прежних получателей. Смена ACL отменяет старый scope UI до запуска новых чтений.
    Изменение состава Workspace, роли, организации или блокировка пользователя обновляют/закрывают существующие соединения. При истечении JWT соединение закрывается; бесконечный retry с тем же токеном запрещён.
    При logout или смене пользователя UI закрывает stream, отменяет запросы и очищает данные/очереди предыдущего пользователя. В первой версии нет требования нового refresh-token механизма.
    REST списка/счётчика/прочтения уведомлений и статуса операции повторно проверяет текущие права. Недоступные цели исключаются из выдачи и непрочитанного счётчика; сохранённое preview не обходит ACL.

8. UI recovery: subscribe → ready → REST reconciliation.
    После stream.ready UI перечитывает активные представления и summary уведомлений. До завершения сверки данные не считаются восстановленными.
    Invalidation помечает соответствующую query/resource как dirty. События объединяются; один event не обязан создавать отдельный HTTP-запрос.
    Если событие пришло во время запроса, dirty сохраняется и после завершения выполняется повторное чтение. При ошибке dirty не теряется; применяются retry/backoff.
    На один resource/query допускается один активный refetch. Invalidation того же scope не увеличивает generation отмены текущего запроса: его разрешённый ответ можно показать, затем повторить чтение при dirty. Generation изменяется при смене пользователя/Workspace/query или отзыве доступа. Coalescing имеет верхнюю задержку и ограничение частоты: постоянный поток событий не должен бесконечно отменять запросы или откладывать обновление до тишины.
    Повторная сверка нужна после reconnect, возвращения вкладки, смены Workspace и восстановления Kafka pipeline. Периодическая редкая сверка активных данных остаётся страховкой; при отказе SSE включается ограниченный polling.
    Скрытая вкладка не опрашивает переписку; накопленные изменения согласуются при возвращении. Новые сообщения дочитываются до прежней границы без пропуска страниц.
    Сохраняются generation guards, защита A → B → A, локальные версии отправки/retry, черновик, прокрутка, фильтры, сортировка и membership. Произвольные push DTO не подменяют состояние.
    Подписки неактивных экранов не вызывают полный refetch всего приложения. При их открытии выполняется обычная REST-загрузка.

9. Центр уведомлений: ограниченный продуктовый объём.
    Сохраняются: назначение диалога адресату; новое LIVE-входящее назначенному сотруднику; окончательная ошибка отправки ответственному сотруднику; канал требует действия — SUPER_ADMIN своей Organization с правом управления подключением. Категория итога отдельной ручной длительной операции зарезервирована и не активируется обычной пагинацией истории. Точная первоначальная семантика N1–N5 и отсутствие broadcast для свободных приняты в NOTIFICATION_SEMANTICS.md.
    При отсутствии ответственного у ошибки отправки получатели определяются каталогом сценариев по текущим правам руководителей. Повторные сигналы одной ошибки не создают пачку записей.
    Новые сообщения обновляют Inbox. Каталог отдельно определяет mobile-alert сценарий нового LIVE-сообщения назначенному сотруднику: при включении сценария создаётся общее персональное уведомление, пригодное для web и native, и push delivery. Для свободных диалогов аудитория задаётся отдельным явным правилом; рассылка каждому руководителю по умолчанию отсутствует. Группировка push по диалогу не удаляет записи центра.
    Импорт истории, периодическая фоновая синхронизация и подгрузка очередной страницы не создают персональные уведомления или всплывающие сообщения об успехе. Ошибка обычной подгрузки показывается в её контексте.
    Минимальная модель: id, recipientEmployeeId, organizationId, workspaceId при наличии, type, targetType/targetId, безопасные templateArgs, createdAt, readAt, alertExpiresAt, deduplicationKey. AlertExpiresAt ограничивает всплывающий/push alert, не срок хранения записи в центре.
    Контент формируется из известных типов и безопасно отображаемых аргументов; HTML и произвольные URL из источника не исполняются. Ссылка строится UI из типизированной цели и проверяется REST при переходе.
    Список имеет стабильную keyset-пагинацию по (createdAt, id). Это пагинация записей, а не курсор доставки SSE. Счётчик вычисляется по доступным непрочитанным записям; отдельный счётчик-проекция пока не нужен.
    Прочтение одного/всех синхронизируется между сессиями через notifications.invalidated. Для одной записи readAt задаётся один раз. «Прочитать все» требует Idempotency-Key: в одной транзакции фиксируются notificationcommand(recipient, key, requestHash, result), обновление доступных записей одним SQL-снимком и outbox. Повтор того же ключа в объявленном окне возвращает исходный результат без нового UPDATE; другой requestHash отклоняется. Новое нажатие создаёт новый ключ. Уведомления, зафиксированные после первого UPDATE, остаются непрочитанными и при повторе запроса. Граница — снимок UPDATE первой команды, а не время открытия списка и не createdAt/max(id).
    Список/summary/read используют одну и ту же ACL-семантику; фильтрация и счётчик выполняются в БД без загрузки всех уведомлений и N+1-проверок. Изменение ACL инвалидирует также загруженные страницы; keyset pagination не обещает замороженный снимок всех страниц между запросами.
    UI: кнопка и счётчик в AppLayout, список всех/непрочитанных, пагинация, loading/empty/error/retry, клавиатура, доступные подписи, мобильное представление, корректный переход между Workspace.
    Всплывающее сообщение — только для новой значимой live-записи после первоначальной сверки; дедупликация по notificationId. Reconnect/загрузка старых страниц не воспроизводят старые всплывающие сообщения. Звук отключён.
    Создание даёт персональный notifications.created с resource(kind=notification, id); read/read-all, ACL и очистка дают notifications.invalidated. Для SSE-alert недостаточно получить created после ready: проверяются серверная граница допустимости новых alert текущей stream-сессии, разрешённый REST DTO, readAt/alertExpiresAt, актуальность категории и сохранённый ограниченный dedup по аккаунту/notificationId. Точный контракт границы задаётся в 11.2 без browser replay/cursor. Повтор старого created после reconnect/reload не даёт новый баннер; на границе reconnect допустима потеря баннера с сохранением записи в центре. Обычная загрузка списка/счётчика не доказывает новизну. Push и SSE используют общий notificationId/dedup; exactly-once показа и единственный баннер между вкладками не обещаются. Основание: R04.
    Удаление/архивирование пользователем и гибкие настройки типов не входят в базовый API. Базовое разрешение push на конкретной установке входит в её регистрацию; OS permission хранится как подсказка, а не как гарантия показа. Retention уведомлений, delivery и outbox настраивается отдельно.

10. Контракты первой версии.
    Browser event: eventId, schemaVersion, type, occurredAt; workspaceId и resource(kind, id) только при необходимости и разрешённом доступе; correlationId при наличии.
    Пример: messages.invalidated для разрешённого conversationId. Другие семейства: inbox, clients, channels, workspace, identity/access, notifications, history-operation.
    notifications.created содержит только разрешённую ссылку на notificationId; read и resync не переиздаются как created. Задержанная доставка created не продлевает alertExpiresAt.
    Внутренние routing-поля/получатели и Kafka-команды в browser event не переносятся. occurredAt служит диагностике, а не определяет порядок или полноту доставки.
    Control events: stream.ready с серверной границей допустимости новых SSE-alert, stream.heartbeat, stream.resync-required. Граница не является курсором полноты доставки; DTO определяется в 11.2. Access invalidation минимальна и не раскрывает недоступную сущность.
    Неизвестный type не ломает UI: ограниченная общая сверка и диагностика. Несовместимая версия переводит клиент на безопасный fallback, без бесконечных reconnect.
    GET /api/events — SSE для текущего пользователя, с разрешённой областью текущего Workspace; персональные notification/access-сигналы не ограничены выбранным Workspace.
    GET /api/notifications — список с unreadOnly, limit и pageCursor; GET /api/notifications/summary — доступный unreadCount.
    GET /api/notifications/{id} — разрешённая текущему пользователю запись и типизированная цель для открытия push; отсутствие записи/доступа не раскрывает приватные данные.
    PUT /api/notifications/{id}/read — идемпотентное прочтение; PUT /api/notifications/read-all — команда с обязательным Idempotency-Key и объявленным окном безопасного повтора.
    PUT /api/push/installations/{installationId} — авторизованная регистрация/обновление своей установки; DELETE /api/push/installations/{installationId} — отвязка. Получатель определяется текущим пользователем на BE, произвольный recipientEmployeeId клиентом не задаётся. Правила владения установкой и смены аккаунта обязательны.
    POST /api/conversations/{id}/history-sync — принять ограниченную операцию и вернуть 202 с operationId; GET /api/history-sync-operations/{id} — актуальный статус/результат.
    GET /api/conversations/{id}/history-sync-operations?activeOnly=true — дополнительный поиск своих незавершённых операций при текущем доступе к диалогу. Для потери 202 клиент сохраняет Idempotency-Key до POST: повтор POST с тем же ключом/параметрами возвращает исходную operation, включая SUCCEEDED/FAILED, в объявленном окне. Active-only discovery не восстанавливает уже завершённый результат. Статус/результат виден инициатору с текущим доступом; доступ иных ролей задаётся явно. Повтор с иными параметрами отклоняется, после истечения окна/очистки поведение определяется контрактом без обещания бесконечного повтора. Основание: R05.
    Это целевые endpoints: точные DTO/OpenAPI и совместимость с текущим sync-history API фиксируются в 11.2 до изменения UI.

11. History Sync — отдельная ограниченная миграция.
    Текущее ожидание Kafka-результата в process-local CompletableFuture заменяется сохраняемой history operation; ответ не должен зависеть от экземпляра сервера или открытого HTTP-запроса.
    Принимающая транзакция сохраняет operation и outbox-команду, затем немедленно возвращает 202. Ждать выполнения команды внутри этой транзакции запрещено.
    Состояния: PENDING, RUNNING, SUCCEEDED, FAILED. Сохраняются operationId, инициатор, conversationId, входной cursor/limit, request deduplication key, timestamps, lease/deadline, безопасная ошибка и результат страницы.
    Повтор POST с тем же ключом/параметрами в объявленном окне возвращает ту же операцию, в том числе terminal; повтор Kafka-команды/результата безопасен. До истечения окна сохраняется связь ключа с исходной операцией/результатом. Протухшие операции получают определённый terminal outcome, а не остаются RUNNING бессрочно.
    Worker получает attempt/claimVersion и проверяет права инициатора перед внешним вызовом/повтором. Timeout/watchdog и ответ worker соревнуются через условное обновление ожидаемого состояния/version; SUCCEEDED/FAILED неизменяемы. Запоздалый результат после FAILED либо от прежнего claim не переводит операцию обратно в RUNNING/SUCCEEDED и не завершает новую попытку.
    Импорт допустимо фиксировать ограниченными транзакциями: частично сохранённая история при ошибке остаётся кэшем с origin HISTORY_IMPORT. Финальная операция публикует SUCCEEDED только после всех требуемых сохранений; это не обещание атомарного rollback всей внешней истории. Watchdog и consumer/DLQ используют тот же протокол состояний.
    SUCCEEDED фиксируется только после сохранения импортированных сообщений и historyStartReached; изменение статуса и его UI invalidation атомарны. Ошибки, исчерпание повторов и DLQ согласуются со статусом операции.
    UI ожидает статус через invalidation + GET, с polling при деградации транспорта; после reload может восстановить незавершённую подгрузку. Уже сохранённая история читается без внешнего канала, с прежними ACL.
    Origin LIVE/HISTORY_IMPORT/SYNC передаётся явно в путях обработки; давность occurredAt не используется для подавления уведомлений. Подавление применяется ко всем импортным путям, включая Recent Chats Sync.
    Сквозной origin реализуется и проверяется в 11.5–11.8 до включения N2, независимо от срока миграции history operations. В 11.10 выполняется повторная регрессия; перенос origin только в конец этапа не допускается. Основание: R06.
    Существующие sync run/lease механизмы Recent Chats переиспользуются по смыслу; универсальная система задач, отмена внешнего запроса и расписания в этот этап не включаются.

12. Подготовка Android/iOS: общее ядро и сменные каналы доставки.
    Notification policy, ACL, notificationId, readAt и REST API общие для браузера и native. Одна персональная запись обслуживает несколько устройств; прочтение на телефоне отражается в web и обратно. Kafka consumer на клиенте отсутствует.
    Android: FCM для устройств с соответствующей поддержкой. iOS: APNs; возможна отправка через FCM как посредника, использующего APNs. Выбор FCM для обеих платформ либо прямого APNs фиксируется при интеграции. PushProvider не привязывает бизнес-логику к одному SDK; устройства Android без Google-сервисов требуют отдельно выбранного адаптера.
    Минимальная регистрация: installationId, текущий recipientEmployeeId/organizationId, platform, provider, appId/environment, provider registration reference, bindingVersion, endpointVersion, enabled, reportedPermission, updatedAt/lastSeenAt. Секреты регистрации защищены от выдачи другим клиентам и логирования. Один сотрудник может иметь несколько активных установок.
    Учитываются выдача/ротация provider registration, переустановка, смена пользователя и logout. Binding version изменяется при перепривязке; старые задания не отправляются на новую привязку. InstallationId сам по себе не является доказательством владения, provider token не является учётными данными пользователя. Контракт регистрации включает проверку владения и защиту от произвольной перепривязки чужой установки.
    EndpointVersion меняется при ротации provider reference или смене app/environment/provider. Попытка отправки фиксирует использованную endpointVersion; ответ провайдера отключает регистрацию только условным UPDATE той же версии/reference. Ошибка старого token не отключает уже обновлённый endpoint. Активный endpoint уникален по (provider, appId, environment, provider-reference fingerprint); совпадение не создаёт вторую активную регистрацию и не переносит её произвольному аккаунту.
    При logout приложение пытается отвязать установку до удаления credentials и очищает локальные уведомления/данные; при logout offline BE может узнать об этом только позднее. Регистрации имеют настраиваемый срок активности и серверный отзыв. Уже принятый провайдером push гарантированно отозвать нельзя.
    Поэтому payload по умолчанию содержит общий текст «Есть новое уведомление», opaque notificationId и schemaVersion, без текста переписки, имени клиента, JWT и приватных target-данных. Push-provider credentials находятся только на BE. При открытии проверяются текущий аккаунт и ACL через REST; чужая/недоступная цель не открывается.
    notificationdelivery: notificationId, registrationId + bindingVersion, channel/provider, status, attempts, claimVersion, nextAttemptAt, leaseUntil, expiresAt, providerMessageId и безопасный errorCode; попытка хранит snapshot endpointVersion. UNIQUE(notificationId, registrationId, bindingVersion, channel) исключает повторное создание задания. Статусы: PENDING, IN_FLIGHT, PROVIDER_ACCEPTED, RETRY, FAILED, CANCELLED, EXPIRED.
    Worker перед отправкой проверяет текущие права, enabled/актуальную привязку и актуальность уведомления. Уже прочитанные или неактуальные задания могут отменяться до отправки; гонка с уже отправленным push допустима и не меняет readAt.
    Retry с backoff/jitter ограничен expiresAt; постоянная ошибка регистрации отключает соответствующий endpoint, transient failure повторяется, ошибка payload не трактуется автоматически как невалидность token. Учитываются Retry-After/rate limits, TTL и допустимая группировка. Ошибка канала не блокирует REST/SSE/создание уведомления.
    Delivery expiresAt не позже notification.alertExpiresAt; provider TTL на каждой попытке не превышает остаток expiresAt - now. Retry не продлевает актуальность события. Ответ ACCEPTED не запускает повтор из-за отсутствия client-open/read. Если endpoint обновился при прежнем владельце, ещё не завершённое задание может использовать новую endpointVersion в следующей разрешённой попытке без создания нового логического delivery.
    После crash между отправкой и записью provider ack повтор push возможен: exactly-once не обещается. notificationId используется для client deduplication и замены системного уведомления, где это поддерживается ОС; grouping/collapse не заменяет серверную идемпотентность.
    В foreground native-клиент объединяет SSE и push по notificationId и не показывает два баннера. Наличие SSE не служит основанием навсегда подавить push: соединение не доказывает внимание пользователя. В background приложение не держит polling; восстановление и открытие push вызывают REST-сверку, авторизацию и затем безопасный переход.
    Read/unread счётчик берётся из REST, а не накапливается арифметически из push. OS badge и удаление уже показанных уведомлений на других устройствах рассматриваются как best effort; чтение в центре не гарантирует немедленное удаление системного баннера.
    Provider ack, показ баннера и нажатие не меняют readAt автоматически. Клиент вызывает общий read API после разрешённого открытия/просмотра по согласованному UX; прочтение сообщения остаётся самостоятельной бизнес-операцией.
    В Stage 11 закладываются модель, API регистрации, интерфейс PushProvider и worker с тестовым адаптером. Реальные SDK/credentials/production adapters и lifecycle мобильного приложения добавляются при его интеграции. Переход к production push требует отдельной приёмки Android/iOS, а не только mock-тестов BE.

КРИТЕРИИ ПРИЁМКИ

    — Изменения из HTTP и Kafka видны другим разрешённым сессиям; недоступные организации, Workspace, диалоги и личные объекты не раскрываются.
    — Rollback не даёт phantom event/notification; crash relay до/после Kafka ack не теряет сохранённое уведомление и не создаёт его дубль.
    — Reconnect, отказ Kafka при живом HTTP, restart сервера, rebalance, потеря вкладкой видимости и смена Workspace приводят к REST-сверке.
    — Событие во время REST-загрузки/ошибки не теряет dirty; перестановка/повтор не откатывают статусы и не возвращают закрытые данные.
    — Работают две сессии одного пользователя, два разных сотрудника, supervisor и SUPER_ADMIN; проверены два gateway с отдельными группами.
    — Отзыв доступа очищает активный UI и центр/счётчик; JWT expiry и logout завершают stream и старые запросы.
    — Центр сохраняет записи после перезапуска/reload, корректно читает одну/все, переживает одновременный приход новых записей и переход к удалённой/недоступной цели.
    — Web/native используют один notificationId/readAt и REST-контракт; push intents не размножаются по числу SSE gateway, а уникальны для notification/registration/binding/channel.
    — Проверены владение регистрацией, несколько устройств, смена аккаунта/отзыв binding, невалидная регистрация, retry/TTL и безопасный payload после отзыва доступа; потеря push не препятствует последующей REST-сверке.
    — Для будущего native-релиза отдельно обязательны реальные Android/iOS проверки: foreground/background/terminated/force-stop по ограничениям ОС, разрешение/отказ, offline, resume/cold start по нажатию, переустановка, дубликаты SSE+push. Гарантия пробуждения при любом состоянии ОС не заявляется.
    — History Sync завершается/ошибается с сохраняемым статусом после смены экземпляра; импорт не создаёт notification storm; обычная пагинация истории не спамит центр.
    — Медленный клиент/массовый импорт не блокирует Kafka consumer, не создаёт неограниченные очереди и не вызывает запрос на каждый event.
    — Определён воспроизводимый нагрузочный профиль и измерены p95 задержки, количество REST-запросов и ресурсы. Численные SLO/лимиты фиксируются до нагрузочной приёмки, без заявления неподтверждённой производительности.
    — Пройдена регрессия Inbox: ACL, сообщения/доставка/retry, история, группы, фильтры, прокрутка, черновик и защита A → B → A.
    — Повтор read-all с тем же Idempotency-Key не читает уведомление, появившееся после первой команды; смена payload по ключу отклоняется. Проверяется фактический snapshot SQL, а не предположение о едином снимке всей READ COMMITTED транзакции.
    — Сигнал очистки приходит после удаления target/membership; проверка доступа к несуществующему target не блокирует разрешённый scope invalidation.
    — Lease takeover, поздние worker results и старая ошибка push endpoint не перезаписывают новые версии/terminal states. Retry передаёт только остаток TTL.
    — LIVE/HISTORY_IMPORT в обоих порядках создают максимум одно разрешённое LIVE-уведомление; повтор после retention центра не возвращает удалённое уведомление и не отправляет старый push новому устройству.
    — Непрерывный поток invalidation не вызывает starvation UI/refetch; после потери ответа POST незавершённая history operation находится серверным discovery API.
    — Read/resync не создают новый alert; задержанный notifications.created не показывает уже прочитанное/просроченное уведомление и не продлевает TTL push.
    — Повтор LIVE после A→B или null→B использует первоначальную аудиторию, включая пустую; импорт не закрывает право первого LIVE принять решение.
    — Поздний FAILED/SENT прежнего sendAttemptId не изменяет новую попытку и не создаёт для неё N3; неоднозначный callback не связывается по одному messageId.
    — Отзыв прав проверяется при задержанной Kafka-инвалидации кэша; отказ авторитетной policy/БД не разрешает чувствительную отправку из кэша.
    — Старый created после нового ready/reload подавляется границей stream и сохранённым dedup даже до expiry; на границе reconnect допустима потеря баннера при сохранении центра.
    — Завершённая до восстановления history operation возвращается по исходному Idempotency-Key; карантин outbox наблюдаем, не блокирует другие записи и не превращается в ложный published.

ПОВТОРНОЕ АРХИТЕКТУРНОЕ РЕВЬЮ — 21.10.2026

    Сохранены: общее ядро web/native, SSE invalidation + REST reconciliation, транзакционные уведомления/outbox, независимая push delivery, серверный ACL и ограниченная история операций. Дополнительный event replay/микросервис не требуется для выбранных гарантий.
    Исправлены пробелы спецификации:
        P1 — read-all был назван идемпотентным без устойчивой границы повтора; добавлены request key и атомарная команда.
        P1 — ACL по удалённому target мог подавить очистку UI; добавлен минимальный scope invalidation прежней области.
        P1 — истёкший lease/поздний history result мог перезаписать новый результат; добавлены claimVersion и терминальные условные переходы.
        P1 — поздняя ошибка старого push token могла отключить новый; добавлены endpointVersion и условная обработка provider response.
        P2 — recovery после потери operationId не имел discovery API; добавлен поиск своих активных операций.
        P2 — непрерывный поток invalidation мог отменять каждый refetch; отделены dirty от смены scope и закреплён single-flight без starvation.
        P2 — очистка центра и гонка LIVE/HISTORY_IMPORT могли нарушить дедупликацию; разделены срок жизни дедуп-маркера и записи центра, а также наличие сообщения и создание LIVE-уведомления.
        P2 — изменение счётчика/списка не отличало новое уведомление от прочтения или resync; добавлены минимальное notifications.created и единый срок актуальности alert без повторного баннера из старых записей.
    Это ревью архитектурного плана, не подтверждение готовности кода. Реализация, concurrency-тесты, нагрузочные пределы и реальная native-приёмка остаются работой по указанным подэтапам.
