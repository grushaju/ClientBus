Пользователь зафиксировал маппинги, отдельную схему `crm`, границы чатовой интеграции и согласовал исправление восьми замечаний двух ревью. Остальные CRM-проекции и команды относятся к следующим подэтапам. Поддержка команд DIKIDI не объявляется доказанной.

## 1. Границы

ClientBus хранит общую идентичность клиента и связывает её с проектными карточками внешней CRM. Внешняя CRM ведёт услуги, предложения мастеров, рабочие графики и визиты. Локальная база содержит представления этих данных, связи и состояние синхронизации.

В этап 12 входят просмотр и синхронизация CRM, а также создание, перенос и отмена визита после проверки соответствующих возможностей. Изменение каталога, графиков, продаж и проведение платежей в объём не входят. Чтение финансового контекста конкретного визита входит; самостоятельная бухгалтерия не создаётся.

Чаты DIKIDI и `DikidiChannelConnector` относятся к этапу 13. В этапе 12 подключение CRM работает без создания Channel, ChannelAccount, ClientAccount или Conversation.

## 2. Проект и подключение

Перечень известных CRM и перечень доступных подключений разделены. `CrmType` содержит DIKIDI, AMO и BITRIX; `AvailableCrmType` в текущем объёме содержит только DIKIDI и явно связывает его с `CrmType.DIKIDI`. Наличие известного типа не означает реализованный адаптер. UI предлагает типы из доступного перечня сервера; backend независимо запрещает подключение AMO/BITRIX до их реализации. Доступность типа не подменяет возможности отдельных операций проекта.

| Объект | Назначение и владелец |
|---|---|
| Organization | Существующая организация ClientBus; владелец CRM-подключений и общих Client |
| CRM-подключение | Доступ к провайдеру: логин, защищённый секрет, состояние авторизации. Не является Employee |
| CRM-проект | Устойчивая локальная идентичность внешнего проекта и его связь с Workspace |
| Workspace | Существующая область работы сотрудников и проверки доступа |

Одно подключение может обслуживать несколько доступных ему проектов. Возможность автоматического перечисления проектов DIKIDI пока не подтверждена: допустим явный ввод ID с проверкой доступа и данных проекта.

Для DIKIDI один подключённый проект соответствует одному Workspace; в одном Workspace не может быть двух проектов DIKIDI. Существующие Workspace могут оставаться без CRM. Уникальность проекта DIKIDI в Workspace обеспечивается ограничением только для этого провайдера; общий запрет нескольких проектов будущего провайдера в Workspace не вводится. Политика других провайдеров определяется отдельно.

Идентичность проекта в ClientBus определяется Organization, провайдером и внешним project ID. Она не включает логин, пароль или локальный ID подключения. Смена секрета и переподключение того же проекта под другим доступом сохраняют локальный project ID, Workspace, маппинги и загруженную историю. Глобальная уникальность произвольных ID провайдеров не предполагается.

Отключение останавливает новые внешние обращения, но сохраняет привязку и историю. Уже начатый внешний эффект обрабатывается по правилам контекста и неопределённого результата ниже. Автоматический перенос проекта в другой Workspace или подмена его другим внешним проектом не выполняются: это затрагивает историю и права и требует самостоятельного сценария. В базовой схеме уникальность привязки сохраняется и для отключённого проекта.

Сессии и CSRF изолированы по подключению и версии учётных данных. Выбранный проект передаётся явно для каждого обращения. Авторизованный доступ к одному проекту не означает доступ к другому. Смена учётных данных инвалидирует прежнюю сессию; поздний ответ старой проверки не восстанавливает прежнее состояние подключения.

Для DIKIDI проверка доступа в новой сессии включает инициализацию выбранного проекта через GET оболочки owner journal в том же cookie-контексте перед чтением R01. Ошибка ACCESS_DENIED при прямом R01 до этой инициализации сама по себе не доказывает отзыв доступа или истечение сессии. Инициализация не отменяет проверку содержимого последующего ответа и не заменяет явно передаваемый project ID.

Каждая задача чтения и команда фиксирует контекст доступа: локальный project ID, внешний project ID, `connectionId`, `credentialVersion` и `contextVersion` проекта. Одинаковая версия секрета у разных подключений не делает их контексты взаимозаменяемыми. Смена подключения проекта, отключение и исправление timezone увеличивают `contextVersion`; смена секрета увеличивает `credentialVersion` и инвалидирует все задачи со старой версией. Контекст проверяется перед обращением и атомарно перед применением результата. Поздний ответ старого контекста не обновляет данные, покрытие, ошибки или состояние нового подключения.

Команда, ещё не начавшая внешнее изменение, при устаревшем контексте отклоняется до эффекта; её нельзя незаметно продолжить под другим подключением. Уже начатое изменение сохраняет исходный контекст, не переносится и не повторяется после переподключения. Его результат сохраняется как результат исходной операции; обновлять актуальное представление проекта можно только через проверку текущего контекста и безопасную сверку. Сверка через новый подтверждённый доступ допустима для того же внешнего проекта и тех же зафиксированных идентификаторов, но не является разрешением повторить команду.

## 3. Внешние идентификаторы

Внешние ID — непрозрачные строки; локальные первичные ключи — UUID. Мастер, услуга и визит уникальны внутри локального CRM-проекта; для клиента дополнительно учитывается установленный тип внешней идентичности. Одинаковая строка ID в разных проектах или типах сущностей не означает один объект. Проектная карточка и системный пользователь DIKIDI не объединяются по числовому совпадению; неизвестная область ID не угадывается и не участвует в автоматическом сопоставлении.

Для DIKIDI разделены:

- project/company ID;
- ID проектной CRM-карточки клиента;
- chat user ID и ID учётной записи доступа;
- ID мастера и услуги каталога;
- ID визита, продажи, строки продажи и платежа.

`client_map_id` различался у двух визитов одного клиента и не используется как ID человека. `added_user_id` обозначает автора действия и не доказывает, что он же клиент визита. CRM client ID не записывается в `ClientAccount.externalId` как chat user ID.

## 4. Клиент CRM и общий Client

`crm.client` хранит внешний профиль, исходное отображаемое имя, контакты и необязательную ссылку на `dbo.client`. Это проектная карточка; она существует независимо от переписки и от наличия общей карточки Client.

Один внешний CRM-клиент связан не более чем с одним Client. Один Client может иметь несколько внешних карточек, в том числе дубли источника; они не схлопываются автоматически. Визиты сохраняют ссылку на исходную карточку и при общем Client отображаются вместе без дублирования одного визита.

Нормализованный телефон используется для поиска кандидатов только в текущей Organization. Совпадение телефона, имени или username не устанавливает связь само по себе. Исходный телефон сохраняется; номера с неоднозначной страной не нормализуются по догадке.

Действия сотрудника:

1. Связать внешнюю карточку с доступным существующим Client.
2. Явно создать Client и связать его с внешней карточкой в одной транзакции.
3. Запросить исправление уже установленной связи; замена и снятие связи требуют руководителя Workspace или SUPER_ADMIN.

Во втором сценарии сотрудник подтверждает поля имени/фамилии и телефонов для текущей модели Client. Исходное полное имя остаётся в CRM-профиле; оно не разрезается автоматически и не обрезается до ограничений полей Client. Изменение источника не перезаписывает общую карточку и не удаляет её телефоны. Отдельное обновление Client использует существующие правила ClientBus.

Изменение связи требует актуальной версии внешней карточки, фиксирует сотрудника и время. Визиты не копируются: их общая принадлежность Client вычисляется через текущую подтверждённую связь. Поэтому исправление связи меняет отображение истории; оно должно быть явным и подтверждённым.

## 5. Мастер и Employee

`crm.master` хранит внешнего мастера и необязательную ссылку на Employee той же Organization. Один Employee может соответствовать мастерам разных проектов. Импорт не создаёт User/Employee и не изменяет `EmployeeWorkspace`.

Маппинг означает соответствие человека, оказывающего услугу. Он не назначает Conversation, не делает мастера supervisor и не выдаёт доступ к Workspace. Техническая учётная запись DIKIDI, мастер, ответственный за диалог и автор сообщения имеют разные назначения.

## 6. Правила чатов, учтённые для этапа 13

Автор уже хранится в `MessageEntity.employee`, колонка `dbo.message.employeeid`, и передаётся в `MessageDto.employeeId`. Новое поле не требуется.

Из ClientBus сообщения отправляют только пользователи с ролью EMPLOYEE, имеющие актуальный доступ к Workspace и назначение на Conversation. SUPER_ADMIN по-прежнему не отправляет сообщения из ClientBus. Право чтения и управления назначениями не подменяет право отправки.

При создании исходящего сообщения Employee берётся из серверной аутентификации. Назначение проверяется атомарно с принятием отправки. Последующее переназначение, обработка очередью и повторная доставка не заменяют автора текущим ответственным.

При импорте старых сообщений владельца DIKIDI `MessageEntity.employee = NULL`. Нельзя подставлять SUPER_ADMIN, мастера или ответственного за Conversation. Внешняя роль `support` зависит от контекста диалога и сама по себе не определяет владельца.

Ревью выявило недостаток проверки назначения в обычной отправке на BE; это отдельное замечание общей чатовой части. Исправление не выдаётся за реализованное в 12.2. Действующий запрет отправки для SUPER_ADMIN дефектом не является.

## 7. Услуги, график и доступность

Каталог услуги и предложение мастера разделены. Одна услуга может иметь разные цену и длительность у разных мастеров. Импорт не оставляет только первое предложение и не применяет цену каталога ко всем мастерам.

Повторное чтение DIKIDI подтвердило два мастера, три услуги и четыре предложения: M1–S1, M1–S2, M2–S2, M2–S3. Общая S2 — одна услуга с двумя предложениями; её цена 10 000 RUB и длительность 60 минут у обоих мастеров одинаковы. Разные значения одной услуги у разных мастеров остаются обязательным сценарием проверки, а не объявляются уже наблюдавшимся фактом.

Состояние предложения (`offerState`) описывает известные признаки активности и публикации для онлайн-записи; неизвестный признак не равен false. Цена, валюта, длительность и дополнительные подтверждённые атрибуты провайдера, включая `floating`, сохраняются отдельно. Это состояние не сообщает о наличии свободного времени. Новый общий enum доступности предложения по одному наблюдавшемуся набору не вводится.

Для DIKIDI источник связи мастер–услуга — каталог кабинета R01. R11 возвращает мастеров с доступностью под условия запроса, а не полный справочник предложений. Пустые R11/R13/R14/R17 не удаляют мастера или предложение и не сбрасывают его active/online. В исследованном наборе у M1 есть активные опубликованные предложения, хотя запросы свободного времени их не возвращают. Совпадение owner ID услуги, online `id` и `company_service_id` подтверждено для трёх услуг этого проекта; оно не становится общим правилом идентичности всех проектов DIKIDI.

Рабочий интервал показывает график мастера. Занятость показывает существующие визиты или подтверждённые блоки. Доступный слот — результат отдельного запроса провайдеру с точными условиями: проектом, списком услуг, выбранным мастером либо явным поиском среди мастеров, датой/периодом и контекстом записи. Локальное вычитание занятости из смены не считается подтверждённой доступностью. Наличие отдельных слотов для S2 и S3 не доказывает возможность совместной записи на обе услуги: сочетание проверяется отдельно.

Если провайдер вернул только время начала, конец доступного интервала не выдумывается и не объявляется подтверждённым сложением длительностей услуг. Начала и подтверждённые интервалы различаются в модели результата. Ответы R11/R14 могут содержать собственный горизонт ближайших дат; такой lookahead не означает полное покрытие запрошенного диапазона. Например, дата 2 декабря в ответе R11 не противоречит графику/запросу R13 до 30 ноября. Условия и фактическое покрытие каждого ответа сохраняются независимо.

Отсутствие услуг/мастеров/смен в отдельной неполной секции не удаляет прежние данные и не снимает ручные маппинги. Смена без внешнего ID хранится как элемент снимка конкретного мастера и периода; глобальная стабильность её ID не придумывается.

Повторяющиеся даты полученных смен не преобразуются в придуманное правило еженедельного повторения. Наблюдавшиеся 11 смен двух мастеров подтверждают конкретные интервалы, но нулевые перерывы и пустые ресурсы не доказывают поддержку непустых перерывов, нескольких интервалов дня, ресурсов или перехода суток. Новых доказательств IANA timezone это чтение не дало.

R17 подтвердил разделение графика и слотов: для M1 вернулись рабочие интервалы 09:55–10:05 без доступных начал; для M2 услуга S2 дала начало 12:00 при смене 12:00–13:00, а сочетание S2+S3 — те же смены без слотов. Вложенный `timeworks` этого ответа — наблюдение графика в собственном горизонте, а не обещание полного графика периода. Наличие `id` смены не доказывает стабильность ID, а поле `server_from` не устанавливает timezone или UTC-смещение проекта.

## 8. Визит и состояния

Визит хранит внешний ID, связь с проектом и внешним клиентом, интервалы, участников-мастеров, услуги и исторические значения. Несколько услуг и мастеров не сводятся к одной записи каталога. Название и цена старого визита не меняются при обновлении каталога.

Запись источника имеет отдельный вид: `APPOINTMENT`, `RESERVATION`, `BLOCK` или `UNKNOWN`. Классификация опирается на подтверждённые признаки провайдера; наличие времени, мастера или клиента само по себе не доказывает вид объекта. Клиентская история включает только подтверждённые `APPOINTMENT`. Резервы, служебные блоки и неизвестные объекты могут отображаться как занятость с соответствующей подписью, если их интервалы достоверны. Они не превращаются в визиты и не допускаются к командам создания/переноса/отмены визита. Внешний резерв, полученный в ходе команды создания, остаётся отдельным шагом операции, пока не подтверждён собственно визит.

| Измерение | Нормализованные значения | Правило |
|---|---|---|
| Состояние визита | UNKNOWN, SCHEDULED, CANCELLED, DELETED | CANCELLED и DELETED различаются; используются только доказанные признаки |
| Подтверждение | UNKNOWN, UNCONFIRMED, CONFIRMED | Отдельно от посещения и оплаты |
| Посещение | UNKNOWN, NOT_RECORDED, ARRIVED, NO_SHOW | Только по установленному отображению кодов |
| Оплата | UNKNOWN, UNPAID, PARTIALLY_PAID, PAID | Выводится из подтверждённых сумм/состояний, не из общего status ID |

Исходные коды и признаки сохраняются рядом с нормализованными состояниями. В проверенном DIKIDI `status_id=1` встречался у оплаченного и неоплаченного визита; его нельзя объявить признаком оплаты или завершения услуги. Установлены отдельные значения посещения 1/2 и отдельный признак подтверждения; остальные отображения требуют доказательств.

Завершение времени визита не означает, что клиент пришёл, услуга оказана или запись оплачена. Непустой ID продажи не означает отсутствие долга. Отсутствие визита даже в полной выборке ограниченного периода не доказывает отмену: его могли перенести за границу периода.

Наблюдаемость объекта отделена от его бизнес-состояния: `OBSERVED` — объект подтверждён чтением, `NOT_OBSERVED` — прежний объект не найден в более новой полной применимой выборке, `UNKNOWN` — достоверного вывода пока нет. Сохраняются время последнего положительного наблюдения и scope/поколение последней проверки. `NOT_OBSERVED` означает необходимость сверки, а не отмену, удаление или подтверждение прежнего времени. Положительный ответ по объекту может восстановить `OBSERVED`; отсутствие в частичной или невалидной выборке не меняет наблюдаемость.

Групповые и другие непроверенные формы не сплющиваются до одного клиента. Если адаптер не может корректно нормализовать участников, он возвращает неподдержанную форму и неполноту соответствующей выборки; при доступном времени/мастерах можно показать ограниченную информацию о занятости. Полнота клиентской истории и команды для таких объектов не обещаются.

## 9. Время и деньги

Время источника сохраняется как локальные дата/время проекта. IANA timezone берётся из подтверждённых данных провайдера либо явной настройки руководителя с отметкой источника. В исследовании DIKIDI timezone не установлен. Часовой пояс сервера, браузера, язык и телефон не заменяют timezone проекта.

До определения timezone локальное время можно показать с предупреждением о неопределённом часовом поясе; соответствующие UTC-моменты остаются неизвестными, команды бронирования недоступны. После определения timezone исходные локальные значения сохраняются. Для неоднозначного или несуществующего локального времени нельзя молча выбирать смещение.

Первое назначение и исправление ошибочной timezone увеличивают `zoneRevision` и `contextVersion`. Исходные локальные значения сохраняются, а производные UTC-моменты помечаются `derivedZoneRevision` — версией зоны, по которой вычислены. С момента изменения старые производные значения не считаются актуальными и не используются для команд или как достоверное время в UI; пересчёт выполняется по сохранённым локальным значениям с новой версией. Неоднозначные значения остаются неизвестными до разрешения. Ожидающие команды со старым контекстом отклоняются до эффекта; уже начатые операции сохраняют первоначальные параметры и требуют сверки. Этот сценарий исправляет настройку; реальный исторический переход проекта в другой часовой пояс требует отдельного правила и не переписывает всю историю автоматически.

Внутренние длительности нормализуются в секунды. В DIKIDI корневая длительность журнала и вложенные длительности имели разные единицы; преобразование задаётся для каждого поля и endpoint отдельно.

Денежные суммы — BigDecimal с валютой, в JSON — десятичные строки. Отсутствующее значение, пустая строка источника, NULL и числовой ноль различаются до нормализации. Недостающая сумма не заполняется нулём.

## 10. Финансовый контекст визита

Финансовый снимок хранится у визита отдельно от его услуг: продажа, строки продажи, скидки, итог, оплата, долг и фактические компоненты платежей. У него собственные время наблюдения, полнота и ошибка обновления. Это нормализованный ограниченный документ, а не сырой HTML и не финансовая книга.

Строка продажи имеет собственный ID, отдельный от ID услуги. Скидка строки не заменяется нулевой скидкой услуги каталога или заголовка продажи. Проверенный пример 5 000 → скидка 30% / 1 500 → итог и оплата 3 500 → долг 0 служит контрольным сценарием, а не правилом расчёта всех продаж.

Из формы платежа извлекаются фактические заполненные компоненты; пустые шаблоны других методов оплатой не являются. Изначальные нули в HTML-итогах до расчёта JavaScript не используются как бизнес-суммы. HTTP 200 с формой новой продажи вместо запрошенной, экраном тарифа или чужой сущностью считается ошибкой контекста/недоступностью.

Смешанные платежи, возвраты, несколько строк/продаж и полнота списка платежей пока не доказаны. Снимок не объявляется полным на основании одного найденного платежа. Ошибка отдельного финансового чтения не удаляет визит и ранее подтверждённый снимок.

## 11. Права CRM

Для CRM действуют существующие роли; новую систему ролей не вводим. SUPER_ADMIN ограничен своей Organization, supervisor — своим Workspace. Отсутствие запроса из UI не заменяет проверку на BE.

| Действие | EMPLOYEE — участник Workspace | Supervisor этого Workspace | SUPER_ADMIN своей Organization |
|---|---|---|---|
| Просмотр CRM и локального финансового контекста | Да | Да | Да |
| Запрос обновления в пределах лимитов | Да | Да | Да |
| Первое подтверждение связи CRM-клиента с Client / явное создание Client | Да | Да | Да |
| Замена/снятие установленной связи с Client | Нет | Да | Да |
| Сопоставление мастера с доступным Employee | Нет | Да | Да |
| Подключение, секрет, привязка проекта, настройка timezone | Нет | Нет | Да |
| Создание/перенос/отмена визита при доступной возможности | Да | Да | Да |
| Чтение операции | Своя | Все операции Workspace | Все операции Organization |

Разрешение SUPER_ADMIN на CRM-команды не разрешает отправку чатовых сообщений. Назначение Conversation не является условием работы с визитом: CRM доступна самостоятельно. Общий Client читается по существующему правилу Organization; его визиты фильтруются по доступным Workspace. Кандидаты маппинга также проходят действующие проверки Client/Employee.

Уточнение UI, согласованное 02.11.2026 в рамках 12.4.1: основной раздел CRM содержит рабочие представления услуг и мастеров. Обычный EMPLOYEE не видит административную таблицу мастер–Employee, её счётчики, фильтр несвязанных или действия назначения. ADMIN в текстах макета соответствует существующей роли SUPER_ADMIN. Управление аккаунтами остаётся в настройках Organization, привязками проектов — в настройках Workspace. В основном разделе CRM режим «Связи с сотрудниками» доступен SUPER_ADMIN и супервизору именно текущего управляемого Workspace; в другом доступном Workspace супервизор получает рабочий справочник без этого режима.

Несопоставленный мастер доступен для просмотра вместе со своими услугами: наличие Employee не является признаком доступности мастера у провайдера. Сопоставление человека, ответственность за Conversation и выбор мастера при записи клиента — разные действия. Это UI-уточнение не отменяет описанные выше права на первое подтверждение связи CRM-клиента с Client, обновление данных или будущие команды визитов. Макет с вымышленными данными не расширяет права доступа к кандидатам и не определяет возможности будущих адаптеров.

Принятый макет — [12-crm-settings.html](ui/mockups/12-crm-settings.html); сценарии и критерии — [эргономическое ревью](ui/mockups/12-crm-ergonomics-review.md). Перенос в приложение завершён и проверен 03.11.2026 как UI-дополнение 12.4.1.

Права проверяются при принятии команды и перед внешним изменением. Начавшийся внешний эффект нельзя отменить отзывом доступа задним числом; его результат сохраняется, а дальнейшее чтение ограничивается актуальными правами. Операция не хранит JWT пользователя как средство доступа к провайдеру.

## 12. Синхронизация и свежесть

Результат загрузки содержит фактический scope: проект, набор, фильтр и период. `COMPLETE` относится только к этому scope; `PARTIAL` и `UNKNOWN` не означают полную историю. Успешная порция не доказывает завершение пагинации. Пустой список сам по себе не доказывает последнюю страницу.

Повторный импорт выполняет upsert по устойчивым ключам проекта и внешнего ID, сохраняет ручные связи и не создаёт дубли Client. Поля, не включённые в ответ, не затираются. Полный снимок графика мастера/дня может атомарно заменить именно этот снимок; правило не переносится на отмену/удаление визитов.

Состояние хранит последнюю попытку и последнее успешное подтверждённое покрытие отдельно. Ошибка не продвигает покрытие и не стирает прежние данные. Свежесть определяется порядком начатых запросов и подтверждённым контекстом, а не порядком прихода ответов.

Обновления объединяются по общей области записи проекта: `APPOINTMENTS` включает календарь, клиентскую историю, чтение отдельного объекта и результат сверки команды; `FINANCE` охватывает финансовый снимок и выводимые из него суммы/состояние оплаты. Разные scope чтения одного визита не получают независимое право перезаписывать его. Для каждой области назначается монотонное поколение до первого внешнего чтения, а полный цикл загрузки и применения сериализуется. Применение и продвижение покрытия атомарно проверяют поколение и контекст в БД; ответ старого владельца выполнения после сбоя или перезапуска отбрасывается. Одна JPA-версия строки эту гарантию не заменяет.

Поколение не даёт неполному источнику права стирать более точные поля. Для каждого источника определены маска присутствующих полей и подтверждённые полномочия их обновлять: список не заменяет отсутствующими или предположительными значениями подробные сведения. Явное очищение допускается только при доказанном значении «пусто» для этого поля. `APPOINTMENTS`, включая клиентскую историю, не меняет финансовый снимок и состояние оплаты, даже если ответ R02 содержит суммы. Такой ответ может запланировать отдельное обновление `FINANCE`, но не становится его доказательством под новым поколением. Финансовая загрузка получает своё поколение до собственного I/O и сама читает актуальные R02 и необходимые F01/F02/F03; прежние ответы не получают новую свежесть через передачу другой задаче. Ошибка одной области не делает успешной другую; свежесть финансового снимка и визита независимы.

После полной валидной выборки отсутствующие ранее известные объекты отмечаются `NOT_OBSERVED` только там, где её фильтр, период и состав действительно позволяют ожидать эти объекты. Проверка наблюдаемости подчиняется тому же порядку поколений. Локальная строка и её последнее подтверждённое состояние сохраняются. Свежий период не делает свежим отсутствующий объект: UI показывает необходимость сверки и время последнего наблюдения, отличая такую строку от подтверждённого актуального визита. Частичная страница, неизвестное покрытие и ошибка ничего не доказывают об отсутствующих объектах.

Первичная загрузка, актуальные периоды, клиентская история и старые периоды имеют отдельные scope. Для DIKIDI фильтр R05 по клиенту пока ненадёжен; R16 доказал совпадение двух будущих визитов, но не полноту истории. UI показывает фактическое покрытие, а не обещание «все визиты».

Сетевой сбой и недоступность внешней сессии не разлогинивают пользователя ClientBus и не уничтожают локальные данные. Внешние чтения имеют ограниченный retry только при доказанной безопасности операции; числовые лимиты определяются при реализации, а не выдаются за обнаруженные ограничения DIKIDI.

## 13. Команды и неопределённый результат

Создание, перенос и отмена разделены. Доступность команды зависит от проверенного протокола, доступа подключения и текущих условий проекта; известное название метода SDK не включает возможность.

Принятие команды, резерв слота, начало изменяющего запроса и подтверждение визита — разные состояния. Локальная идемпотентность защищает повтор запроса ClientBus; она не доказывает внешнее exactly-once.

UI сохраняет ключ действия вместе с проектом и текущим пользователем до первого запроса и сохраняет его при перезагрузке страницы до терминального результата. Потеря ответа с ID операции восстанавливается повтором того же запроса с тем же ключом либо поиском по ключу; список своих активных операций проекта позволяет найти незавершённую операцию при утрате локального состояния. Оба способа чтения повторно проверяют текущие права. Тот же ключ с другим содержимым отклоняется; новый ключ не создаётся автоматически после timeout, переподключения или обновления страницы. Неопределённый результат не является терминальным; UI восстанавливает состояние этого действия и предлагает сверку существующей операции, а не повтор как новую команду. Явное новое действие после разрешённого терминального результата получает новый ключ.

До команды проверяются актуальные данные провайдера и доступность. Это не является внешним CAS или гарантией отсутствия параллельной записи. Неизвестные поля, услуги, цены, статусы и связь с продажей не сбрасываются неполной формой переноса.

После начала изменяющего запроса timeout, потеря соединения/ответа и авария процесса дают `UNKNOWN`, пока нет однозначного доказательства результата. Автоматический повтор, в том числе после авторизации, запрещён. Восстановление выполняет безопасную сверку того же объекта/ключа и целевого состояния; отсутствие объекта в диапазоне не считается доказательством неуспеха.

Для DIKIDI резерв, его TTL/освобождение, сохранение, перенос и семантика отмены ещё требуют W-проверок. Нельзя заменить отмену физическим удалением. До доказательства команда имеет состояние возможности `UNVERIFIED` и не отправляется провайдеру.

## 14. Хранение и UI-обновления

Новые CRM-таблицы размещаются в `crm`; существующие бизнес-сущности остаются в `dbo`, служебная схема `system` сохраняется. Межсхемные FK связывают CRM с Organization/Workspace/Employee/Client. Схема БД не заменяет проверки прав.

Физическое удаление Client безопасно снимает только необязательные маппинги `crm.client.clientid` в той же транзакции и с соблюдением прав на все затрагиваемые Workspace; внешний профиль и его визиты сохраняются. Если нужных прав нет, операция отклоняется без частичного снятия связей. Удаление Employee аналогично снимает необязательные маппинги мастеров, но исторические ссылки на инициатора операции и автора маппинга не обнуляются: при таких ссылках физическое удаление блокируется понятным `409`, сотрудника можно отключить через `employee.user.enabled` (`dbo.users.isenabled=false`). Снятие маппинга фиксирует прежнюю связь, инициатора и время и публикует событие; импорт не восстанавливает её автоматически. Удаление Workspace с привязанным CRM-проектом, в том числе отключённым, блокируется `409`. Эти правила включаются в существующие CRUD-пути до появления CRM-связей; каскадное удаление CRM-истории при удалении Client/Employee/Workspace/Organization запрещено.

Физические имена таблиц, колонок, индексов и ограничений — без `_`. Java-классы имеют префикс Crm; таблицы внутри схемы его не повторяют. Общий Hibernate `default_schema=dbo` сохраняется, CRM явно задаёт схему. Таблицы создаются через `ddl-auto=update`; создание самой схемы и запуск на пустой/существующей БД проверяются в 12.3 без новых миграций.

Применённые изменения публикуют одно агрегированное workspace-событие через существующий outbox/SSE. Оно инвалидирует CRM-представления, но не передаёт секреты/финансовые документы и не создаёт персональные уведомления для каждой импортированной строки. UI использует существующую отмену запросов и защиту от поздних ответов при смене Workspace/учётной записи и отзыве доступа.

## 15. Проверки перед включением

Контракты проверяются на повторном импорте, переподключении без дублей, нескольких карточках одного Client, несопоставленных мастерах/клиентах, разных предложениях одной услуги, исторических значениях визита, скидке и отдельном платеже, неполной странице/периоде, неизвестном timezone, изоляции Workspace и неопределённой команде.

Дополнительные обязательные сценарии согласованного ревью:

1. Переключение подключения A → B с одинаковым числом `credentialVersion`, смена секрета, отключение и поздние ответы: старые чтения/ожидающие команды не применяются, начатое изменение не повторяется под новым доступом.
2. Медленная история клиента и свежее чтение календаря одного визита, отдельно — финансового снимка: общий порядок записи и полномочия источников защищают новые данные и не стирают подробности.
3. Потеря первого ответа с ID операции, обновление страницы и утрата локального состояния: находится та же операция, новый внешний визит не создаётся.
4. Перенос визита за пределы периода и его отсутствие в новой полной выборке: `NOT_OBSERVED`, предупреждение в UI и последующая положительная сверка вместо ложной отмены. Частичная выборка не меняет наблюдаемость.
5. Удаление связанного Client, Employee — мастера и исторического автора, Workspace с отключённым проектом: атомарное снятие только допустимых связей либо понятный `409`, сохранение истории и события.
6. Первое назначение и исправление timezone при сохранённых визитах и ожидающих/начатых командах: старые UTC-моменты сразу недействительны, исходное локальное время сохраняется, пересчёт не пропускает неоднозначные значения.
7. Визит, резерв, блок и объект неизвестного вида: корректная занятость без попадания технических объектов в клиентскую историю и без допуска к командам визита.
8. Один проект DIKIDI на Workspace и сохранение связи при смене доступа; ограничение DIKIDI не применяется к будущему провайдеру без отдельного решения.

Сценарии по повторному чтению DIKIDI: два мастера/три услуги/четыре предложения сохраняются без дубля общей S2; пустой результат S1 не снимает её предложение; отдельные слоты S2 и S3 не заменяют запрос их сочетания; ближайшая дата за пределами периода не расширяет доказанное покрытие; повторяющиеся смены не создают рекуррентного правила. Это сценарии будущей реализации, а не уже выполненные тесты ClientBus.

Матрица фактических A/W-проверок и их ограничения остаются в [CRM_DIKIDI_PROTOCOL.md](CRM_DIKIDI_PROTOCOL.md). Проектирование контрактов не меняет их на «выполнено». Реализация следующего подэтапа начинается после отдельного согласования его плана.
