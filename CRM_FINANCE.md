# Финансы визита — backend 12.4.5

Финансовые данные читаются отдельно от календаря. Суммы из прежней загрузки APPOINTMENTS/CLIENT_HISTORY не получают новую дату наблюдения и не применяются как финансовое обновление.

## API

- `GET /api/crm/appointments/{id}/finance` — локальный снимок и состояние FINANCE. `id` — UUID визита ClientBus.
- `POST /api/crm/appointments/{id}/finance/refresh` — ограниченное синхронное чтение и применение свежего снимка; тело запроса отсутствует. Вызов не создаёт продажи или платежи в DIKIDI.

Доступ имеет участник Workspace и SuperAdmin своей Organization. Права проверяются до I/O и заново при записи. При потере доступа старый ответ не публикуется. Вызов по неизвестному/чужому ресурсу не выполняет внешних запросов.

Ответ `CrmFinanceDto` содержит `appointmentId`, `snapshot`, `observedAt`, `completeness`, `sync`. Снимок версии 1 включает `saleReference`, точный `scope`, `lines`, `totals`, `payments`, `sections`, `warnings`; валюта документа расположена в `totals.currency`. Поля с неизвестными суммами равны null, нули не подставляются. `sync` отделяет успешное наблюдение от последней попытки, ошибок, поколения и свежести. Ошибка сохраняет прежний снимок и дату успешного наблюдения. Смена подключения/контекста/timezone или клиента/даты визита делает прежний снимок STALE.

## Чтение DIKIDI

Адаптер заново читает R02 точной даты и проверяет ID, вид визита, принадлежность проекту и клиента. Только после этого следует `info.payment.document_id`:

1. F01: GET `/ru/owner/ajax/sales/form/{saleId}/?company={project}`. Hidden `sale_id` и клиент `table=clients/table_id` должны совпасть. Строки услуг сопоставляются внутри своего HTML-контейнера; одинаковые имена input из разных строк не соединяются по индексам.
2. F02: POST `/owner/ajax/sales_payments/get_list/`, только `company`, `sale_id`, `isEdit=false`. Ссылки создания нового платежа без ID пропускаются и не запрашиваются. ID имеющихся платежей извлекаются из проверенных ссылок текущего проекта/продажи.
3. F03: GET формы существующего платежа. Принадлежность определяется hidden `sale_id/payment_id`; внешний JSON `id` обозначает UI-диалог. Пустые заготовки способов оплаты не становятся платежами.

Точные итоги cost/paid/debt берутся из собственного свежего R02. Цена, процент скидки, сумма скидки и итог строки берутся отдельно из существующей продажи. Нулевые `total-endpay` и другие заготовки для вычислений JavaScript игнорируются. Выручка не пересчитывается из исходной цены услуги. Валюта перечитывается для выбранного проекта. Неизвестные способы/форматы, отсутствующий документ или недоступные платежи оплаченного визита дают ошибку возможности, сохраняя прежний результат.

Уточнение после ревью 07.11.2026: отсутствие ID существующих платежей в F02 отклоняется при любом `paid`, включая 0 и неизвестную сумму. Пустой HTML, форма авторизации, сообщение о недоступности и одна ссылка добавления не подтверждают пустой список оплат. Пока отдельный формат корректного пустого F02 не подтверждён, такой результат возвращает CAPABILITY_UNVERIFIED и сохраняет прежний финансовый снимок.

Денежные значения преобразуются с `USE_BIG_DECIMAL_FOR_FLOATS`. В JPA финансовый документ представлен raw JSON string в прежнем столбце JSONB, чтобы стандартная десериализация `Map<String,Object>` Hibernate не превращала дробные числа в Double. Getter/setter и публичный DTO сохраняют объектный формат снимка; новых столбцов и преобразования существующих документов нет. Точность проверяется до записи, непосредственно в PostgreSQL, после чтения в новой транзакции и после последующего обновления календаря. Существующие JSON-объекты и null-поля читаются в прежнем формате.

Полнота всех секций DIKIDI остаётся UNKNOWN: на текущем аккаунте подтверждены одна строка услуги и одна оплата наличными. Смешанные документы, возвраты, групповые/системные клиенты и полнота списка платежей не объявляются подтверждёнными. Финансовые команды save/pay/remove не реализованы. Прикладной экран относится к 12.5.

## Применение и конкуренция

Используются существующие поля `crm.appointment` и `crm.syncstate`; новых таблиц нет. Один CONTROL `WRITER:FINANCE/CONTROL` на проект выдаёт общее поколение и lease 120 секунд до сетевого чтения. Публичный scope FINANCE относится к UUID одного визита. Сетевые запросы выполняются вне DB-транзакции с общим лимитом адаптера 75 секунд.

Перед применением повторно проверяются connectionId/credentialVersion/contextVersion/zoneRevision, полномочия автора, версия визита, поколение и действующий claim. Lease проверяется по времени PostgreSQL, в том числе после flush. Истёкший или вытесненный ответ не применяется; следующий запрос может занять истёкшую аренду после перезапуска.

FINANCE меняет только financialsnapshot/financialobservedat/financialgeneration/financialcompleteness/paymentstate и собственное состояние синхронизации. Исторические услуги, комментарии, время и наблюдаемость календаря сохраняются. Состояние PAID/PARTIALLY_PAID/UNPAID выводится только при известных согласованных cost/paid/debt и валюте; иначе UNKNOWN. Применение публикует `crm.invalidated` через существующий outbox.
